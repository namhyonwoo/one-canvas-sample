# 통합캔버스 (one-canvas) 작성 규칙

## 파일을 어디에 만드는가 (디렉터리 구조)

통합캔버스는 **`one-canvas/<기획-건>/canvas-*.html`** 에 만든다. 기획 건 폴더 하나 안에 그 건에서 갈라진 에픽별 캔버스 파일이 모인다.

```
one-canvas/
├── one-canvas-rule.md          ← 이 규칙 문서
├── sample/                     ← 규칙 참고용 예시 (실무 산출물을 여기 두지 않는다)
│   ├── partner-settlement/
│   ├── cart-price-change-alert/
│   └── restock-alert/
│
├── order-cancel/               ← 실무 기획 건
│   ├── canvas-admin-order-cancel.html
│   └── canvas-app-order-cancel.html
└── member-join/
    └── canvas-app-member-join.html
```

### 규칙1

- **폴더 = 기획 건(작업 단위)** 이며 **도메인이 아니다.** 도메인은 문서 안의 「도메인」 소제목이 이미 담당하므로 폴더까지 도메인으로 나누면 중복이다. 실제로 폴더명과 도메인은 자주 다르다 — 예: `restock-alert` 폴더 / 도메인 `product (상품)`, `cart-price-change-alert` 폴더 / 도메인 `cart (장바구니)`.
- 폴더명은 **영문 kebab-case**로 짓고, 그 기획 건을 알아볼 수 있는 기능·요청 이름을 쓴다. `canvas-` 접두어는 붙이지 않는다(파일명 전용).
- **에픽이 갈리면 파일이 늘고, 폴더는 하나로 유지한다.** 「에픽 명세 수준」의 "캔버스 1개 = 에픽 1개" 원칙 때문에 한 기획 건에서 캔버스가 여러 개 나오는 것이 정상이다. 예: 파트너 정산 → 목록/요약/상세 3개 + 배치 1개가 `partner-settlement/` 한 폴더에 모인다.
- **화면 없는 캔버스(B유형)도 같은 폴더에 둔다.** 별도 폴더로 분리하지 않는다 — 같은 기획 건의 산출물이기 때문이다.
- **`sample/` 은 규칙 예시 전용**이다. 실무 캔버스를 `sample/` 하위에 만들지 않는다.
- 폴더가 이미 있으면 새로 만들지 않고 그 안에 파일만 추가한다. 기획 건이 새로 시작될 때만 폴더를 만든다.
- 파일명 규칙은 아래 「화면(디자인) 작성 규칙」(A유형) / 「B. 화면이 없는 경우」(B유형)를 따른다.

> 2단계 agile-issue는 폴더 계층이 다르다 — 거기서는 `<도메인>/epic-*/story-*/` 로 **도메인**이 최상위다(agile-issue-rule.md 참고). 1단계는 기획 건 단위로 묶고, 2단계에서 도메인 단위로 재배치되며, 둘을 잇는 것은 폴더가 아니라 에픽 `캔버스:` 줄이다(이 파일 경로가 에픽↔캔버스 라우팅의 단일 출처다).

## 형식을 지킬 수 없으면 질문한다 (필수)

이 문서가 요구하는 형식·항목을 **추측으로 채우지 않는다.** 채울 근거가 없으면 작성을 멈추고 **반드시 질문한다.**

**왜 이 규칙이 필요한가**: 통합캔버스는 2단계 agile-issue의 **단일 출처**다. 근거 없는 내용이 캔버스에 한 줄 들어가면, 그 전제에서 에픽·유저스토리·수락 기준(AC)·태스크·테스트가 줄줄이 파생된다. 캔버스에서 한 줄 지어내는 비용보다 파생물 전체를 되돌리는 비용이 훨씬 크다.

### 판정 기준 — 근거가 문서에 있는가

| 상황 | 처리 |
|---|---|
| 요구사항·기존 문서·화면에 **근거가 있다** | 스스로 판단한다. 판단이 갈릴 여지가 있었다면 `(근거: …)`를 함께 적는다 |
| 근거가 없어 **지어내야 한다** | **질문한다.** 답이 오기 전에는 그 항목을 확정하지 않는다 |

이 기준은 새로 만든 것이 아니라, 이미 유저스토리 규칙(`문서에 없는 조건·정책을 GWT가 새로 지어내지 않는다`)에 있던 원칙을 문서 전체로 일반화한 것이다.

### 질문 대신 하기 쉬운 금지 행동

- ❌ **빈칸을 그럴듯한 문장으로 채우기** — 가장 흔하고 가장 위험하다. 나중에 누가 정한 정책인지 아무도 알 수 없고, 리뷰에서도 걸러지지 않는다.
- ❌ `TBD` / `미정` 만 적고 **질문 없이** 넘어가기
- ❌ 채울 수 없는 항목·소제목을 **통째로 생략**하기
- ❌ `design-system` 에 없는 컴포넌트를 **있는 것처럼 태깅**하기
- ❌ **화면설명에 백엔드 계약을 정의하기** — 확정되지 않은 API 엔드포인트·응답 필드명·DB 테이블을 「데이터 출처」 자리에 채워 넣기. `전제(확정 필요)`·`명명 제안` 단서를 달아도 마찬가지다 (「화면설명 작성 규칙」 참고)
- ❌ **코멘트용 태깅을 캔버스에 심기** — `data-block` 같은 코멘트 전용 속성을 원본에 넣기. 리뷰 때문에 캔버스 파일이 수정되어 작성자와 git 충돌이 난다 (「코멘트가 블록에 붙어 있으려면」 참고)
- ❌ **형식을 임의로 바꾸기** — 에픽 2개 넣기, 규정에 없는 소제목 추가·삭제 등
- ❌ **디스크립션 두 유형을 합치거나 뒤바꾸기** — 화면설명과 UI 디스크립션을 한 블록에 몰아넣기, 로직 설명을 우측 패널에 넣기, UI 영역 설명을 화면설명에 넣기 (「디스크립션 유형과 위치」 참고)

### 반드시 질문해야 하는 대표 상황

- **에픽 4항목** 중 근거 없는 항목이 있다 — 특히 `제외 범위`·`완료 기준`은 요구사항에 안 나오는 경우가 많다
- **플로우의 분기를 확정할 수 없다** — 에픽 범위·유저스토리 어디에도 근거가 없는 흐름을 그려야 한다. 플로우는 필수 소제목 중 **지어내기가 가장 쉬운 형식**이다(빈 분기를 그럴듯하게 잇는 데 아무 비용이 들지 않고, 리뷰에서도 지어낸 티가 나지 않는다). 근거 없는 노드·분기는 그리지 말고 질문한다
- **도메인**을 못 정하거나 2개 이상에 걸친다 (하나만 적어야 한다)
- **에픽이 1개인지 2개 이상인지** 판단이 안 선다 — 캔버스 파일을 분리할지가 달라진다
- **A/B 유형**(화면 유무) 판정이 안 선다
- 화면 요소에 대응할 **컴포넌트를 못 정한다** / 태깅해야 하는데 후보가 없다
- **GWT를 쓰려는데 문서에 없는 조건·정책이 필요**하다
- **화면 간 관계가 불명확**하다 — 예: 페이지형이 모달을 대체하는지 병행 제공인지
- **입력 경계·예외 동작이 정의되지 않았다** — 예: 시작일 > 종료일 처리, 최대 조회 기간 제한, 데이터 0건일 때 표기
- 파일을 둘 **기획 건 폴더**를 못 정한다

### 질문하면서 진행하는 방법 — 전부 멈추지 않는다

질문해야 한다고 해서 작성 전체를 중단하라는 뜻이 아니다.

- 막힌 **그 항목만** 질문하고, 근거가 있는 나머지는 계속 작성한다.
- 질문했지만 답이 오지 않은 항목은 지어내지 말고 **문서에 남긴다.** 2단계 스토리에서는 `### 열린 질문 (기획 확인 필요)` 섹션으로 기록한다(agile-issue-rule.md 참고).
- 전제를 깔고 진행해야 한다면 **전제를 명시**한다. 예: `본 문서는 병행 제공 전제로 작성했다 — 확정 필요.`
- 질문에는 **무엇이 왜 막혔는지 + 답에 따라 무엇이 달라지는지**를 함께 적는다. 선택지를 낼 수 있으면 함께 제시한다.

## 통합캔버스 문서 구성

통합캔버스(html) 산출물은 **화면(UI) 존재 여부**에 따라 아래 두 가지로 분기해서 구성한다.

### 요구사항 처리 원칙 (A/B 공통)

사용자로부터 받은 요구사항(회의록, 티켓, 채팅 요청, 구두 지시 등)은 원문 그대로 별도 섹션에 나열하지 않는다. 요구사항을 받으면 **반드시 에픽과 유저스토리로 분류해서 서술**한다.

- 여러 기능에 걸치는 상위 목적·범위(In/Out-of-Scope)·완료 기준 → **에픽**으로 정리한다.
- 개별 사용자 동작·시스템 이벤트 단위의 요구사항 → **유저스토리**로 쪼개어 Given-When-Then(GWT) 시나리오로 서술한다.
- 요구사항을 받는 즉시 이 분류 작업부터 수행하고, 통합캔버스에는 분류 결과(에픽/유저스토리)만 반영한다. "요구사항 정의"라는 별도 소제목은 두지 않는다.

### A. 화면이 있는 경우 (통상적인 UI 개발)

아래 6개 소제목으로 구성한다 (요구사항 정의는 위 원칙에 따라 별도 소제목으로 두지 않음).

1. 도메인
2. 에픽
3. 유저스토리
4. 플로우 — 에픽 흐름을 mermaid로. **유저스토리 다음, 화면(디자인) 앞.** 「플로우 명세 수준」 참고.
5. 화면(디자인)
6. 디스크립션(화면당) — **화면설명(화면 하단)** + **UI 디스크립션(우측 패널)** 두 가지로 나뉜다. 둘 중 하나만 쓰지 않는다. 「디스크립션 유형과 위치」 참고.

Figma·엑셀 등 참고할 외부 자료가 있으면 **도메인 바로 다음**에 `참고 자료` 소제목을 추가한다 (없으면 생략).

### B. 화면이 없는 경우 (백엔드/배치/API 등 UI 없는 개발)

아래 4개 소제목만으로 구성한다. 화면(디자인)과 디스크립션(화면당)은 작성하지 않는다.

1. 도메인
2. 에픽
3. 유저스토리
4. 플로우 — 배치/시스템 흐름을 mermaid로. **유저스토리 다음** (B는 화면이 없으므로 문서 마지막). 「플로우 명세 수준」 참고.

A와 마찬가지로 참고할 외부 자료가 있으면 도메인 바로 다음에 `참고 자료` 소제목을 추가한다 (없으면 생략).

- 화면이 없는 경우 유저스토리는 "사용자"가 아니라 **시스템/배치가 주체**가 된다. 스토리 이름은 시스템 관점으로 짓고, 본문 GWT의 When도 시스템 이벤트가 주체다. 예: `Given 반품이 확정된 정산 건이 있고, When 정산 배치가 반품 확정 이벤트를 감지하면, Then 해당 정산 금액을 재계산해 정합성을 유지한다.`
- 아래 `화면(디자인) 작성 규칙`(컴포넌트 태깅·번호 매핑·인터랙션 등)은 해당 없음 — 적용하지 않는다.
- **파일명 규칙**: `canvas-{platform}-{에픽명}-noscreen.html` 형식으로 짓는다. 예: `canvas-partner-settlement-batch-noscreen.html`.
- 참고 예시: `canvas-partner-settlement-batch-noscreen.html` (시스템 관점의 GWT 유저스토리)
  - ⚠️ 이 파일은 **「플로우」 규칙 신설 이전에 작성**되어 도메인/에픽/유저스토리 3개 소제목만 있다. 유저스토리 서술 방식은 참고해도 되지만, **소제목 구성은 위 4개를 따른다.**

### 소제목 접기/펼치기 (A/B 공통, 필수)

**모든 `<h2>` 소제목은 클릭하면 그 아래 내용이 접히고 다시 펼쳐져야 한다.** 캔버스는 도메인부터 화면·디스크립션까지 한 파일에 다 들어가 세로로 길어지므로, 지금 보려는 섹션만 남기고 접을 수 있어야 스크롤 비용이 줄어든다.

- **기본 상태는 전부 펼침이다.** 접힌 채로 열리는 캔버스를 만들지 않는다 — 리뷰 체크리스트는 항목이 문서에 **있는지 눈으로 확인**하는 방식이라(「통합캔버스 리뷰 체크리스트」), 기본 접힘이면 누락과 접힘을 구별할 수 없다.
- **마크업은 손대지 않는다.** `<h2>` 뒤에 내용을 평소대로 나열하면 되고, 문서 하단의 토글 스크립트가 **각 `<h2>`부터 다음 `<h2>` 직전까지를 자동으로 묶어** 접이 영역으로 만든다. 섹션마다 래퍼 `<div>`를 손으로 감싸지 않는다 — 기존 캔버스도 스크립트만 넣으면 그대로 동작한다.
- **스크립트는 문서 전체에 1개만** 둔다(mermaid 로더와 같은 원칙). 소제목마다 핸들러를 따로 붙이지 않는다.
- **접힘 상태가 우측 패널을 깨뜨리지 않게 한다 (A유형 필수)**: UI 디스크립션 패널은 `IntersectionObserver`로 `.screen-block`을 추적하는데(「UI 디스크립션(우측 패널) 규칙」), 「화면(디자인)」이 접히면 관측 대상이 사라져 **패널이 사라진 화면의 디스크립션을 계속 띄운 채 남는다.** 화면 블록을 품은 섹션이 접히면 패널도 함께 숨기고, 펼치면 되돌린다.
- **접근성**: `<h2>`에 `role="button"` · `tabindex="0"` · `aria-expanded`를 부여하고 Enter/Space로도 토글되게 한다. 펼침/접힘 표시(▾/▸)는 CSS `::after`로 붙이고 화면 콘텐츠 텍스트로 넣지 않는다.

```html
<!-- 소제목 접기/펼치기 — 문서 하단에 1개만. mermaid 로더보다 앞에 둔다. -->
<script>
(function () {
  var panel = document.getElementById('descPanel');
  Array.prototype.forEach.call(document.querySelectorAll('body > h2'), function (h2) {
    var body = document.createElement('div');
    body.className = 'sec-body';
    var node = h2.nextElementSibling;
    while (node && node.tagName !== 'H2') {
      var next = node.nextElementSibling;
      body.appendChild(node);
      node = next;
    }
    h2.parentNode.insertBefore(body, h2.nextSibling);

    h2.classList.add('sec-head');
    h2.setAttribute('role', 'button');
    h2.setAttribute('tabindex', '0');
    h2.setAttribute('aria-expanded', 'true');

    var hasScreens = !!body.querySelector('.screen-block');
    function toggle() {
      var open = h2.getAttribute('aria-expanded') === 'true';
      h2.setAttribute('aria-expanded', String(!open));
      body.hidden = open;
      // 화면 블록이 접히면 우측 패널이 사라진 화면을 가리킨 채 남는다 → 함께 숨긴다
      if (panel && hasScreens) panel.style.display = open ? 'none' : '';
    }
    h2.addEventListener('click', toggle);
    h2.addEventListener('keydown', function (e) {
      if (e.key === 'Enter' || e.key === ' ') { e.preventDefault(); toggle(); }
    });
  });
})();
</script>
```

### 도메인 명세 수준 (A/B 공통)

문서 최상단(다른 모든 소제목보다 앞)에 이 통합캔버스가 속하는 상위 비즈니스 도메인을 **도메인** 소제목으로 반드시 기록한다.

- agile-issue-rule.md의 도메인 디렉터리 명명 규칙과 동일하게 **접두사 없이 영문 kebab-case**로 적고, 한글명을 괄호로 병기한다. 예: `settlement (정산)`.
- 하나의 통합캔버스는 하나의 도메인에만 속한다. 여러 도메인에 걸치는 작업이면 통합캔버스 자체를 도메인별로 분리한다.
- 이렇게 도메인명을 명시해두면 2단계(agile-issue) 변환 시 어느 도메인 디렉터리 하위에 에픽/스토리를 생성할지 그대로 매핑되어, 도메인 판단을 다시 하지 않아도 된다.

### 참고 자료 명세 수준 (A/B 공통, 선택)

통합캔버스 작성에 참고한 외부 자료(Figma 디자인 시안, 엑셀 데이터 정의서, 기존 기획 문서, 노션/컨플루언스 페이지 등)가 있으면 **참고 자료** 소제목으로 정리한다. 관련 자료가 없으면 이 섹션 자체를 생략한다.

- 목록 형식: `자료명 — 링크 — 한 줄 설명`
- 예: `Figma 디자인 시안 — https://figma.com/file/xxxx — 화면 3개 hi-fi 시안`, `정산 수수료율 엑셀 — https://docs.google.com/spreadsheets/xxxx — 파트너별 수수료율 정의`
- 링크만 나열하지 말고 각 자료가 무엇인지 한 줄 설명을 반드시 함께 적는다 (나중에 링크가 만료되거나 접근 권한이 없어도 문서만으로 맥락을 알 수 있어야 한다).

### 에픽 명세 수준 (A/B 공통)

**하나의 통합캔버스에는 에픽을 반드시 1개만 적는다.** 한 문서에 에픽 테이블을 2개 이상 두지 않는다.

- 요구사항을 정리하다 에픽이 2개 이상으로 갈라지면, **문서 안에서 나누지 말고 통합캔버스 파일 자체를 에픽별로 분리**한다. 예: 정산 조회가 `목록 조회`와 `상세 조회`로 갈라지면 → `canvas-partner-settlement-list.html` + `canvas-partner-settlement-detail.html`.
- **이유**: ① 파일명 규칙이 `canvas-{platform}-{화면명}.html` 단수형이고, ② 2단계 agile-issue에서 에픽 `캔버스:` 줄이 캔버스 파일 1개를 가리키므로(agile-issue-rule.md 참고) 한 파일에 에픽이 여러 개면 어느 에픽의 변경인지 diff로 가려낼 수 없다. ③ 유저스토리·화면도 에픽별로 갈라져 한 문서 안에서 소속을 계속 표기해야 한다.
- 분리한 캔버스끼리 **화면이 이어질 때**(예: 목록에서 행을 클릭해 상세 진입)는 각 캔버스가 **자기 에픽 범위만 소유**하고, 상대 화면은 진입점 수준으로만 축약해 보여준 뒤 `제외 범위`와 **화면설명**에 상대 파일명을 명시한다(소유 범위는 로직 이야기이므로 우측 패널이 아니라 화면설명이다).
- 도메인·참고 자료는 분리된 캔버스들이 **동일하게 반복 기재**한다(각 파일이 독립적으로 읽혀야 한다).

에픽은 아래 4가지 항목을 반드시 포함해서 작성한다.

- **목적**: 이 에픽을 통해 달성하고자 하는 비즈니스/사용자 목표
- **주요 범위 (In-Scope)**: 이번 에픽에서 실제로 구현하는 범위
- **제외 범위 (Out-of-Scope)**: 이번 에픽에서 다루지 않는 범위와 그 사유(예: 다음 에픽으로 이관, 후속 단계에서 처리 등)
- **완료 기준**: 에픽이 완료되었다고 판단할 수 있는 구체적이고 검증 가능한 기준

### 유저스토리 명세 수준 (A/B 공통)

유저스토리는 **스토리 이름 + Given-When-Then(GWT) 시나리오**로 작성한다. 스토리 이름이 "누가·무엇을·왜"(정체성)를 담고, GWT가 실제 동작을 서술한다. 이 단계에서는 기획자가 파악한 주요 시나리오를 쓰고, 예외 케이스까지 망라한 상세 수락 기준·성공/실패 테스트는 2단계 `agile-issue-rule.md`의 스토리 `index.md`에서 이 GWT를 계승·상세화한다.

- **스토리 이름**: 단순한 작업 제목(예: "정산 조회 기능")이 아니라, **누가(사용자 역할) · 무엇을(행동) · 왜(가치)** 하려는지가 그대로 드러나야 한다.
- **서술 형식(GWT)**: `Given <사전 조건>, When <행동/이벤트>, Then <기대 결과>.`
- 하나의 유저스토리는 하나의 사용자 행동 단위로 쪼갠다. 여러 행동이 섞여 있으면 스토리를 분리한다.
- 하나의 스토리 안에서도 정상/예외 등 조건 분기가 있으면 GWT 시나리오를 분리해 여러 개 적는다.
- GWT는 화면·에픽에 이미 명시된 동작에 근거해서 쓴다. 문서에 없는 조건·정책을 GWT가 새로 지어내지 않는다.

#### 동작 순서 — 쉬운 말로 다시 쓴다 (스토리마다 필수)

**GWT 바로 아래에 그 스토리를 쉬운 말로 단계적으로 서술한 「동작 순서」 블록을 둔다.** 스토리 하나에 하나씩, 예외 없이 붙인다.

**왜 같은 내용을 두 번 쓰는가**: GWT는 조건·이벤트·결과를 한 문장에 압축한 형식이라 **정확하지만 읽는 사람이 순서를 머릿속에서 재구성해야 한다.** 조건 분기가 여러 개인 스토리에서는 "그래서 사용자가 무엇부터 하는가"가 형식에 가려진다. 캔버스는 기획자·디자이너·개발자·QA가 **함께 읽는 문서**이므로, 형식에 익숙하지 않은 사람도 스토리를 따라갈 수 있어야 한다. 이 블록은 **새 명세가 아니라 같은 명세의 다른 표현**이다.

- **형식은 버그 재현 경로와 같다.** 번호 목록(`<ol>`)으로, 한 줄에 한 동작만, `~합니다` 종결의 완결 문장으로 쓴다.
- **마지막 줄은 확인 결과로 끝낸다.** 재현 경로가 "…확인할 수 있습니다"로 끝나는 것과 같다 — 무엇이 보이면 성공인지가 마지막 줄에 있어야 한다.
- **예시**

  ```
  1. 검수 및 결과보고 팝업에 접근합니다.
  2. 검수사진 및 수령 사진 첨부를 시도합니다.
  3. 예시로 A, B, C 3장의 이미지를 첨부합니다.
  4. A, B, C 파일이 첨부됨을 확인할 수 있습니다.
  ```

- **GWT 시나리오 하나당 목록 하나다 (필수).** 스토리에 시나리오가 3개면 번호 목록도 3개다. 하나로 합치면 정상·예외가 뒤섞여 마지막 줄에 결과를 하나만 적게 되고, 나머지 분기의 결과가 사라진다.
  - 시나리오가 2개 이상이면 목록마다 **무슨 경우인지 라벨**을 붙인다(`정상 제출` · `필수 항목 누락` · `사업자번호 중복`). 시나리오가 하나뿐이면 라벨 없이 목록만 둔다.
  - 라벨은 GWT의 `Given`·`When`에서 따온다. 새 분기를 만들지 않으므로 **목록 개수는 항상 GWT 시나리오 개수와 같다** — 개수가 다르면 둘 중 하나가 지어낸 것이다.
- **`Given`은 그 상태에 이르는 동작이 있으면 첫 단계로 푼다.** 예: `Given 정산 내역 목록이 표시된 상태에서` → `1. 정산 내역 목록 화면에 접근합니다.` 사용자가 할 수 있는 동작이 아니면(예: `Given 승인되어 운영 중인 파트너가`) 동작으로 바꾸지 말고 `승인되어 운영 중인 상태에서 시작합니다.` 처럼 전제로 적는다.
- **여기서 번호를 쓰는 것은 예외가 아니다.** 「화면설명 작성 규칙」이 번호 목록을 금지하는 이유는 화면 영역 번호 배지와 혼동되기 때문인데, 동작 순서는 「화면(디자인)」 바깥의 유저스토리 섹션에 있고 화면 영역을 지목하지 않는다. 혼동할 대상이 없으므로 **단계 번호를 그대로 쓴다** — 순서가 이 블록의 본질이고, "3번에서 막힌다"처럼 단계를 지목할 수 있어야 한다.
- **정책을 새로 만들지 않는다 (필수).** GWT에 없는 단계·조건·화면을 여기서 만들어 넣지 않는다. 쉬운 말로 풀다 보면 "그 다음엔 당연히 이렇게 되겠지" 싶은 단계를 채우게 되는데, 그 순간 이 블록이 세 번째 명세 저장소가 된다(「플로우가 정책을 새로 만들지 않는다」와 같은 원칙). 풀어 쓸 근거가 부족하면 지어내지 말고 **질문한다.**
- **GWT가 정본이다.** 둘이 어긋나면 GWT를 따르고, **GWT를 고치면 동작 순서도 같이 고친다.** 한쪽만 고치면 같은 스토리가 두 가지를 말하게 된다.
- **2단계 agile-issue는 이 블록을 계승하지 않는다.** AC는 GWT에서 파생되고, 동작 순서는 명세가 아니라 표현이다. 이슈로 옮기지 않으며 「최신 대조」의 대조 대상도 아니다(agile-issue-rule.md 「용어 정의 — 최신 대조」).
- **B유형(화면 없음)은 주체가 시스템·배치다.** 유저스토리와 같다. 예: `1. 정산 배치가 반품 확정 이벤트를 감지합니다.`
- **`id`는 `steps-<스토리명>`** 으로 붙인다. 다른 `id` 규칙과 같은 이유로 의미 기반이며, 한 번 정하면 바꾸지 않는다(「코멘트가 블록에 붙어 있으려면」). 코멘트는 실제로는 블록이 아니라 **단계 `<li>`에 붙는다** — 지목 단위가 그쪽이다.
- **⚠️ 기존 캔버스에 뒤늦게 추가하면 코멘트 앵커가 흔들릴 수 있다.** 단계 `<li>`가 문서 앞쪽(유저스토리)에 들어가면서 뒤에 있는 모든 `<li>`의 문서 순서가 밀리기 때문이다. 앵커는 텍스트 지문(②)으로 먼저 찾으므로 문구가 그대로인 블록은 살아남지만, 문구까지 바뀐 블록은 순서 폴백(③)이 어긋난다. 그래서 **동작 순서만 일괄로 끼워 넣는 작업은 하지 않고, 그 스토리를 손볼 때 함께 추가한다.**

**마크업 골격**

> ⚠️ **동작 순서가 들어 있는 캔버스는 위 `-detail` 하나뿐이다** — 나머지는 이 규칙 신설 이전에 작성된 파일이라 스토리에 GWT만 있다. 리뷰 체크리스트의 「동작 순서」 항목은 그 파일들에 소급 적용하지 않는다. **기존 캔버스의 스토리를 고칠 일이 생기면 그때 동작 순서를 함께 추가한다**(플로우 규칙을 신설했을 때와 같은 방식).

### 플로우 명세 수준 (A/B 공통, 필수)

**유저스토리 다음, 「화면(디자인)」 앞**에 이 캔버스가 소유한 에픽의 흐름을 **플로우** 소제목으로 반드시 기록한다. A·B 유형 모두 필수이며 생략할 수 없다. (B유형은 화면이 없으므로 플로우가 문서의 마지막 소제목이 된다.)

**왜 유저스토리 다음인가**: 플로우의 노드·분기는 **유저스토리 GWT를 근거로 그린다.** 근거(GWT)를 먼저 읽고 그것을 한 장으로 종합한 플로우를 보는 순서라야 "이 분기가 어디서 왔는지"가 바로 대조된다. 플로우를 앞에 두면 근거를 모른 채 그림부터 보게 되어, 지어낸 분기가 섞여도 걸러지지 않는다. 이어서 「화면(디자인)」이 나오므로 **흐름 → 그 흐름이 실제로 어떤 화면으로 구현되는지**로 자연스럽게 넘어간다.

- **범위 — 에픽 1개의 흐름만 그린다.** 「에픽 명세 수준」의 "캔버스 1개 = 에픽 1개" 원칙이 그대로 적용된다. 여러 에픽의 흐름을 한 다이어그램에 섞지 않는다. 분리된 캔버스와 화면이 이어지는 경우(예: 목록 → 상세)는 상대 에픽을 **진입/이탈 노드 하나로만** 표시하고 그 안을 펼치지 않는다.
- **형식**: `<h2>플로우</h2>` 다음에 `<pre class="mermaid">` 블록을 두고 **mermaid 소스를 평문 그대로** 넣는다. `flowchart TD`가 기본이고, 시간 순서·주체 간 주고받음이 핵심이면 `sequenceDiagram`을 써도 된다.
- **소스는 반드시 평문이다 — 이미지·SVG·외부 파일로 대체 금지.** 두 가지 장치가 소스 텍스트에 의존한다.
  1. **최신 대조**: agile-issue가 에픽 「흐름도」를 이 소스와 직접 맞춰본다(agile-issue-rule.md 참고). 플로우가 렌더된 이미지면 흐름이 바뀌어도 대조할 텍스트가 없어 그 구간에서만 조용히 무력화된다.
  2. **계승**: agile-issue 에픽 `index.md`의 `## 흐름도`가 **이 소스를 그대로 복사해 쓴다**(아래 「2단계 계승」).
- **렌더링 (CDN)**: 실제 도형으로 보이도록 문서 **하단에 mermaid 로더 `<script type="module">` 을 1개만** 둔다. 다이어그램마다 로더를 만들지 않는다.
  ```html
  <script type="module">
    import mermaid from 'https://cdn.jsdelivr.net/npm/mermaid@11/+esm';
    mermaid.initialize({ startOnLoad: true, theme: 'neutral' });
  </script>
  ```
  - 이것은 캔버스 html이 갖는 **유일한 외부 의존**이다. 네트워크가 없으면 다이어그램 대신 mermaid 소스 텍스트가 그대로 보이는데, **그 상태로도 문서는 읽혀야 한다** — 노드 이름을 알아볼 수 없는 축약어로 짓지 않는다.
  - 로더를 빠뜨려도 문서가 깨지지는 않지만(소스가 보임), 규칙상 필수다.
- **(A유형) 노드에 화면 번호를 적는다**: 화면이 있는 캔버스는 화면에 해당하는 노드에 `화면 N`을 병기해 바로 다음에 오는 「화면(디자인)」 섹션과 눈으로 대조되게 한다. 예: `A[화면 1 · settlement-list<br/>정산 내역 목록]`.
- **(B유형) 주체는 시스템/배치다**: 노드가 사용자 행동이 아니라 시스템 이벤트·배치 단계·상태 전이가 된다.
- **플로우가 정책을 새로 만들지 않는다 (필수)**: 모든 노드와 분기는 **에픽 범위 또는 유저스토리 GWT에 근거가 있어야 한다.** 유저스토리 규칙의 "문서에 없는 조건·정책을 GWT가 새로 지어내지 않는다"와 같은 원칙이다. 플로우 차트는 빈 분기를 그럴듯하게 채우기 가장 쉬운 형식이라 특히 위험하다 — 근거가 없는 분기는 그리지 말고 **질문한다**(「형식을 지킬 수 없으면 질문한다」).
- **2단계 계승**: 이 플로우가 agile-issue 에픽 `index.md` `## 흐름도`의 **원본**이다. 2단계에서 흐름도를 새로 그리지 말고 이 mermaid 소스를 그대로 옮긴다(agile-issue-rule.md 「에픽 작성 규칙」 참고).

> ⚠️ **기존 `sample/` 캔버스 중 플로우가 있는 것은 `canvas-partner-settlement-list.html` 하나뿐이다** — 나머지는 이 규칙 신설 이전에 작성된 파일이다. 플로우는 `-list` 쪽과 아래 「플로우 예시」를 따른다. 기존 캔버스를 수정할 일이 생기면 그때 플로우를 함께 추가한다.

## 수정하면 수정일을 남긴다 (A/B 공통, 필수)

**캔버스 내용을 고치면 `canvas-updated-at` 을 그 시각으로 갱신한다.** 확정 여부와 무관하고, 예외는 아래 한 가지뿐이다. 새 캔버스를 만들 때도 작성 시각으로 넣는다 — 처음부터 있어야 "언제 마지막으로 바뀌었나"에 빈칸이 생기지 않는다.

`<title>` 바로 다음, 확정 meta와 같은 자리에 둔다(앞머리 스캔 범위 안에 있어야 하는 이유는 「기록 형식 — `<head>` meta가 정본」과 같다).

```html
<title>통합캔버스 — 비즈니스 정보 등록·수정 (파트너 센터)</title>
<meta name="canvas-updated-at" content="2026-08-10T11:20:00+09:00">
```

**왜 파일 안에 적는가 — git이 알고 있지 않은가**: 알지 못한다. one-canvas는 작업 코드베이스와 **별개 저장소**이고(agile-issue-rule.md 「용어 정의 — 최신 대조」), 툴은 배포 이미지에 복사된 파일을 읽는다. 복사 시점에 파일 mtime과 git 이력은 사라지므로, **파일 안에 적힌 값만 살아남는다.** 캔버스를 열어 보는 사람도 저장소를 클론하지 않고 html만 받는 경우가 많다.

- **형식은 ISO 8601 + 오프셋**이다. 확정 시각과 같은 형식이어야 두 값을 비교할 수 있다.
- **날짜만 적지 않는다.** 같은 날 여러 번 고치는 일이 흔한데, 날짜만 있으면 확정 당일에 수정된 캔버스를 "확정 후 수정됨"으로 판정할 수 없다.
- **시각을 지어내지 않는다 (필수).** AI에게 주어지는 것은 대개 **날짜뿐**이라 `HH:MM:SS`를 채우려면 만들어내야 한다. 지어낸 초 단위 값은 "확정 후 수정됨" 판정을 조용히 오염시킨다 — `date -Iseconds` 처럼 **실제 시각을 얻어서** 쓰고, 얻을 수 없으면 지어내지 말고 묻는다(「형식을 지킬 수 없으면 질문한다」).
- **갱신하지 않는 유일한 예외 — 확정 표기를 넣는 것 자체.** 확정 meta·배지를 삽입하는 것은 기획 내용의 변경이 아니라 사실 기록이다. 여기서 수정일을 함께 올리면 모든 캔버스가 확정되자마자 "확정 후 수정됨"으로 보인다.
- **오타·서식 정리도 수정이다.** 무엇이 "내용 변경"인지 매번 판정하려 들면 결국 아무도 갱신하지 않는다. 캔버스를 저장했으면 올린다고 보면 된다.
- agile-issue의 모든 `index.md`가 frontmatter `updated:` 를 필수로 두는 것과 같은 장치다. 1단계·2단계 문서가 같은 규칙을 갖는다.

### 캔버스 수정 프롬프트

캔버스를 고칠 때 쓰는 프롬프트다. **수정 요청에 이 한 덩어리를 붙이는 것이 수정일을 실제로 강제하는 유일한 지점이다** — 규칙 문서는 읽어야 적용되지만, 프롬프트는 요청과 함께 붙어 다닌다.

```
<캔버스 파일 경로> 를 아래대로 고쳐줘.

[수정 내용]
<무엇을 어떻게 바꿀지>

[고칠 때 반드시 같이 할 것]
- 다 고친 뒤 <head>의 canvas-updated-at 을 지금 시각으로 갱신해줘.
  값이 없으면 <title> 바로 다음에 새로 만들어 넣어줘.
  <meta name="canvas-updated-at" content="...">
  시각은 `date -Iseconds` 같은 걸로 실제 값을 얻어서 써. 지어내지 마.
  형식은 ISO 8601 + 오프셋이고 시:분까지 필요해 (날짜만 적지 마).
- canvas-status · canvas-confirmed-at · canvas-confirmed-issue 는 건드리지 마.
  확정은 이미 일어난 사실이라 캔버스를 고쳐도 바뀌지 않아.
- 블록 id 를 바꾸거나 지운 블록의 id 를 다른 블록에 물려주지 마
  (코멘트가 엉뚱한 블록을 가리키게 된다).
- one-canvas/one-canvas-rule.md 의 형식을 벗어나는 수정이 필요하면 멈추고 물어봐.
```

## 확정 상태 기록 (A/B 공통)

**확정 = 이 캔버스의 기획을 모두 동의한 것으로 보고, 이 캔버스에서 애자일 이슈를 최초로 생성했다.** 사람이 마음대로 켜고 끄는 상태값이 아니라 **"최초 이슈 생성이 일어났다"는 사실의 기록**이다.

**왜 파일 안에 적는가**: 캔버스 파일만 봐서는 아직 논의 중인 초안인지 이미 이슈가 파생된 확정본인지 구별되지 않는다. 리뷰어는 초안에 코멘트를 달다가 사실은 이미 개발이 시작된 문서였다는 것을 뒤늦게 알게 되고, 반대로 확정본인 줄 알고 손대지 않은 문서가 실은 아무도 안 본 초안일 수도 있다. one-tool 캔버스 목록도 같은 정보를 이 기록에서 읽는다.

### 누가 기록하는가

**애자일 이슈를 최초로 생성하는 쪽이 기록한다.** 캔버스 작성자가 "이제 확정이다" 싶을 때 미리 적는 값이 아니다 — 확정의 정의가 이슈 생성이므로, 이슈를 만들지 않은 시점에 확정 표기가 붙어 있으면 그것은 거짓이다. 절차는 agile-issue-rule.md 「캔버스 확정 표기」에 있다.

one-tool은 이 값을 **읽기만 한다.** 캔버스 파일을 쓰지 않는다는 원칙(「코멘트가 블록에 붙어 있으려면」)이 여기에도 그대로 적용된다.

### 기록 형식 — `<head>` meta가 정본

**`<title>` 바로 다음, `<style>` 앞**에 둔다. 위치가 규칙인 이유: 툴은 캔버스 파일 전체를 읽지 않고 **앞머리만 훑어서** 이 값을 찾는다. 대용량 `<style>` 블록 뒤로 밀리면 **오류 없이 조용히 미확정으로 읽힌다.**

```html
<title>통합캔버스 — 비즈니스 정보 등록·수정 (파트너 센터)</title>
<meta name="canvas-status" content="confirmed">
<meta name="canvas-confirmed-at" content="2026-08-04T17:34:52+09:00">
<meta name="canvas-confirmed-issue" content="agile-issue/partner-review/epic-partner-business-info">
<meta name="canvas-updated-at" content="2026-08-10T11:20:00+09:00">
```

| meta | 값 | 비고 |
|---|---|---|
| `canvas-status` | `confirmed` 고정 | 이 meta가 **없으면 미확정**이다. 미확정을 나타내는 값을 따로 두지 않는다 |
| `canvas-confirmed-at` | 최초 이슈를 생성한 시각 | **ISO 8601 + 오프셋** (`2026-08-04T17:34:52+09:00`) |
| `canvas-confirmed-issue` | 그때 만든 에픽 디렉터리 경로 | 에픽 `index.md`의 `캔버스:` 줄과 대칭이 되게 **저장소 루트 기준**(`agile-issue/…`)으로 적는다 |
| `canvas-updated-at` | 이 캔버스를 마지막으로 고친 시각 | **확정과 무관하게 모든 캔버스가 갖는 값**이다 — 아래 「수정하면 수정일을 남긴다」가 소유한다. 확정된 캔버스에서는 이 값이 확정 시각보다 뒤이면 "확정 후 수정됨"으로 읽힌다 |

**시각 형식이 깨지면 시각만 버리고 확정은 유지한다.** 툴은 읽지 못한 시각을 `확정 · (시각 없음)`으로 비워서 보여줄 뿐, 확정 자체를 취소하지 않는다 — 이슈는 실제로 존재하므로 "미확정"이 더 큰 거짓말이기 때문이다. 반대로 `canvas-status` 값 자체가 `confirmed`가 아니면(오타 포함) 미확정으로 읽힌다.

### 기록 형식 — body 최상단 배지

캔버스 html을 툴 없이 직접 열어도 확정 여부가 보여야 한다. `<body>`의 **첫 요소**로 둔다.

```html
<body>
<aside id="canvas-confirm-badge" style="display:inline-block;margin:12px 28px 0;padding:6px 12px;
  border-radius:6px;background:#edfcf2;border:1px solid #a6f4c5;color:#067647;
  font:600 12px/1.4 -apple-system,sans-serif;">
확정 · 2026-08-04 17:34 · agile-issue/partner-review/epic-partner-business-info
</aside>
```

- **`<div>`로 만들면 안 된다 (필수).** 코멘트 앵커의 3순위 폴백은 **태그별 문서 순서**(`h2#3` 같은 값 — 「코멘트가 블록에 붙어 있으려면」 표 ③)인데, 화면설명 `.screen-note`와 UI 디스크립션 `.screen-desc`가 `<div>`다. body 맨 앞에 div를 하나 끼우면 **문서의 모든 div 인덱스가 1씩 밀려 기존 코멘트가 옆 블록을 가리킨다** — 규칙이 "앵커를 잃는 것보다 나쁘다"고 못 박은 바로 그 상황이다. `aside`는 앵커 대상 태그가 아니라 인덱스 계산에 끼어들지 않는다.
- **스타일은 인라인으로 넣는다.** 캔버스마다 CSS가 달라 클래스에 기댈 수 없다. 좌우 여백(`28px`)은 본문 래퍼의 padding에 맞춘 값이라, 캔버스 여백이 다르면 그 값에 맞춰 조정한다.
- `id`는 `canvas-confirm-badge` 하나로 고정한다.

### 확정 명령 — 애자일 이슈 생성까지 한 번에 (필수)

**「확정해줘」는 표기를 바꾸는 명령이 아니라 이슈를 만드는 명령이다.** 확정의 정의가 "애자일 이슈를 최초로 생성했다"이므로, 이슈 없이 확정 표기만 다는 것은 **거짓을 기록하는 것**이다. 그래서 이 명령 하나가 아래 3단계를 순서대로 수행한다.

**트리거**: `확정해줘` · `이 캔버스 확정해줘` · `확정` 등 확정을 지시하는 말. 어느 캔버스를 확정하는지 특정되지 않으면 **진행하지 말고 묻는다** — 엉뚱한 캔버스에서 이슈가 파생되면 되돌리는 비용이 크다.

| 단계 | 하는 일 | 멈추는 조건 |
|---|---|---|
| ① 확정 전 점검 | 「통합캔버스 리뷰 체크리스트」로 캔버스를 훑는다 | 근거 없이 채워진 항목·답을 못 받은 질문·누락된 소제목이 있으면 **멈추고 질문한다** |
| ② 애자일 이슈 생성 | agile-issue-rule.md에 따라 **도메인 → 에픽 → 스토리** `index.md`를 만든다 | 캔버스에 근거가 없어 지어내야 하는 항목이 나오면 멈추고 질문한다 |
| ③ 캔버스에 확정 기록 | 위 형식대로 meta + 배지를 넣는다 | ②가 끝나지 않았으면 **기록하지 않는다** |

- **①에서 멈추는 이유**: 확정은 "이 기획에 모두 동의했다"는 선언이다. 빈칸이 남은 채 확정하면 그 빈칸이 에픽·유저스토리·AC·태스크·테스트로 그대로 증폭된다(「형식을 지킬 수 없으면 질문한다」).
- **②에서 태스크·테스트는 만들지 않는다.** 섹션 자리는 템플릿대로 두되 내용은 비운다 — 태스크는 개발자가, 테스트는 QA가 쓰는 항목이다(agile-issue-rule.md 「계층별 작성 주체(Role) 매핑」). 확정은 기획자 몫의 계층까지만 만든다.
- **③은 반드시 마지막이다.** ②가 중단되면 확정 표기를 남기지 않는다. 표기는 "이슈가 있다"가 참이 된 뒤에만 쓸 수 있는 사실 기록이기 때문이다.
- **이미 확정된 캔버스면 ①에서 끝낸다.** 다시 확정하지 않고, 확정 시각과 이슈 경로를 알려준 뒤 "기획이 바뀌었으면 확정이 아니라 최신 대조로 이슈를 맞춘다"고 안내한다(「확정은 취소하지 않는다」).
- **반대 방향으로 들어와도 끝 상태는 같다.** 캔버스가 아니라 이슈부터 만들기 시작한 경우는 agile-issue-rule.md 「캔버스 확정 표기」가 같은 ③을 요구한다. 어느 쪽으로 진입하든 "이슈가 있으면 캔버스에 확정 표기가 있다"가 유지된다.

#### 확정 실행 프롬프트

```
<캔버스 파일 경로> 확정해줘.

확정 = 이 캔버스의 기획에 모두 동의하고, 여기서 애자일 이슈를 최초로 생성한다는 뜻이야.
표기만 바꾸는 게 아니라 아래 3단계를 순서대로 해줘.

[1] 확정 전 점검
    one-canvas/one-canvas-rule.md 「통합캔버스 리뷰 체크리스트」로 이 캔버스를 훑어줘.
    - 근거 없이 채워진 항목, 답을 못 받은 질문, 누락된 소제목이 있으면
      거기서 멈추고 나에게 물어봐. 그 상태로 이슈를 만들지 마.
    - 이미 확정 meta(canvas-status)가 있으면 여기서 끝내고,

[2] 애자일 이슈 생성

    - 도메인 index.md → 에픽 index.md → 스토리 index.md 순서로.
      (도메인 디렉터리가 이미 있으면 새로 만들지 말고 그 안에 에픽을 추가)
    - 에픽은 캔버스의 「에픽」 4항목 + 「플로우」 mermaid 소스를 그대로 계승해줘.
      흐름도를 새로 그리지 마.
    - 에픽에 `> 캔버스: <이 캔버스의 경로>` 줄을 남겨줘.
    - 스토리는 캔버스 「유저스토리」의 GWT를 계승해서 상세화해줘.
    - 태스크·테스트 섹션은 자리만 두고 비워둬. 개발자·QA가 채우는 항목이야.
    - frontmatter를 빠뜨리지 마 — 모든 계층에 `updated:`, 스토리에는 `status: ready`.
      (확정은 "명세 확정, 개발 착수 가능"이라는 선언이라 draft가 아니라 ready야.
       열린 질문이 남았다면 애초에 [1]에서 멈췄어야 해)
    - 상위 목록도 함께 갱신해줘. 기존 도메인에 에픽을 추가했으면 그 도메인 index.md의
      「하위 에픽」에, 스토리를 추가했으면 에픽 index.md의 「하위 스토리」에 줄을 더해줘.

    - 캔버스에 근거가 없어 지어내야 하는 항목이 나오면 멈추고 물어봐.

[3] 캔버스에 확정 기록
    [2]가 끝난 뒤에만 해줘. 중간에 멈췄으면 이 단계는 건너뛰어.
```

### 확정은 취소하지 않는다

기획이 나중에 크게 바뀌어도 **확정 시각은 그대로 둔다.** "최초 이슈 생성"은 이미 일어난 사실이라 되돌릴 대상이 아니고, 이슈를 지웠다 다시 만들어도 최초 시각이 정본이다. 확정 이후의 변경은 `canvas-updated-at` 만 갱신해서 "확정 후 수정됨"으로 드러낸다.

캔버스와 이슈가 어긋나는 문제는 확정 상태가 아니라 agile-issue-rule.md 「최신 대조(reconcile)」가 담당한다 — **캔버스 HEAD가 항상 정본**이고 이슈를 거기에 맞추는 방식이므로, 상태를 되돌려서 표현할 것이 애초에 없다.

### 새로 만드는 캔버스는 미확정이다

캔버스를 새로 생성할 때 확정 meta·배지를 넣지 않는다. 아직 이슈가 없으므로 정의상 미확정이다. (단 `canvas-updated-at` 은 확정과 무관한 값이라 **새 캔버스에도 넣는다** — 「수정하면 수정일을 남긴다」.)

⚠️ `sample/`의 규범 예시 파일(`canvas-partner-settlement-detail.html` 등)에는 확정 표기를 **넣지 않는다.** 그 파일들은 "새 캔버스는 이 파일 그대로 따른다"고 지정된 참조본이라, 확정 meta가 들어가면 새 캔버스가 그것까지 복사해 이슈도 없이 확정된 문서가 만들어진다.

## 코멘트가 블록에 붙어 있으려면 (A/B 공통)

공동작업 툴(one-tool)은 캔버스의 특정 블록을 지목해 코멘트를 단다. 코멘트 본문은 툴의 DB에 저장되고 **캔버스 html은 읽기만 한다** — 그래야 리뷰어가 코멘트를 달 때마다 캔버스 파일이 수정되어 캔버스 작성자와 git 충돌이 나는 일이 없다.

대신 "어느 블록이었는지"를 기억할 방법이 필요하다. 툴은 코멘트를 저장할 때 **앵커 3종을 함께 남기고**, 다시 찾을 때 위에서부터 폴백한다.

| 순위 | 앵커 | 값의 예 | 무엇에 강한가 |
|---|---|---|---|
| ① | 요소의 `id` | `id:screen-detail` | **문구·순서가 모두 바뀌어도 살아남는다** |
| ② | 텍스트 지문 | `c8c58107` (정규화 텍스트 앞 120자 해시) | 블록이 문서에서 위아래로 밀려도 살아남는다 |
| ③ | 태그별 문서 순서 | `h2#3` | 문구가 수정돼도 살아남는다 |

①②로 찾으면 **확정**이고, ③으로 찾으면 **추정**이라 코멘트 카드에 `⚠ 캔버스가 수정되어 위치를 추정했습니다`가 붙는다. 전부 실패하면 `⚠ 위치를 찾을 수 없습니다`가 붙는다(코멘트 자체는 사라지지 않는다).

이 구조가 제대로 동작하려면 캔버스 쪽에서 지켜야 할 전제가 있다.

- **코멘트를 위한 속성을 캔버스에 심지 않는다 (필수)**: `data-block` 같은 코멘트 전용 태깅을 원본에 넣지 않는다. 앵커는 툴이 렌더 시점에 계산하므로 원본에 있을 필요가 없고, 넣는 순간 **리뷰 때문에 캔버스 파일이 수정되는 구조**로 되돌아간다 — 캔버스 작성자와 리뷰어가 같은 파일을 동시에 건드려 git 충돌이 난다.
- **코멘트를 받을 블록에는 `id`를 붙인다 (필수)**: 위 표의 ①은 **유일하게 문구 수정과 순서 변경을 동시에 견디는 앵커**다. `id`가 없으면 문구와 위치가 함께 바뀔 때 코멘트가 **엉뚱한 블록을 가리킨 채 "추정" 표시만 달고 남는다** — 리뷰어가 잘못된 블록을 보고 논의하게 되므로, 코멘트를 잃는 것보다 나쁘다. 아래 단위에는 문서를 만들 때부터 `id`를 붙인다.

  | 단위 | `id` 예 |
  |---|---|
  | `<h2>` 소제목 | `sec-domain` · `sec-epic` · `sec-story` · `sec-flow` · `sec-screen` |
  | 동작 순서 `.story-steps` | `steps-settlement-detail` (스토리 영어명 그대로) |
  | 화면 블록 `.screen-block` | `screen-settlement-detail` (화면 영어명 그대로) |
  | 화면설명 `.screen-note` | `note-settlement-detail` |
  | UI 디스크립션 `.screen-desc` | `desc-settlement-detail` |
  | 플로우 `<pre class="mermaid">` | `flow-settlement` |
  | 표 `<table>` | `table-epic` · `table-domain` |

  이미 「마크업 골격」의 `<section class="screen-block" id="screen-detail">`이 이 형태다. **`id`는 화면 영어명·소제목 의미에서 따오고, 문서 안에서 유일해야 한다.**
- **`id`는 한 번 정하면 바꾸지 않고, 재사용하지 않는다 (필수)**: `id`를 고치면 그 블록에 달린 코멘트가 전부 앵커를 잃는다. 반대로 삭제한 블록의 `id`를 다른 블록에 물려주면 **예전 코멘트가 엉뚱한 블록에 붙는다** — 앵커를 잃는 것보다 나쁘다. `id`는 화면 영어명처럼 의미 기반으로 짓고(`screen-settlement-detail`), 문구를 다듬을 때도 그대로 둔다.
- **같은 문구를 문서 안에서 반복하지 않는다 (권장)**: 위 표의 ②는 텍스트로 블록을 식별하므로, 소제목이나 표 제목이 문서 안에 똑같이 두 번 나오면 어느 쪽인지 결정할 수 없어 폴백이 한 단계 더 떨어진다. `기본정보` 같은 짧고 흔한 제목을 여러 섹션에서 그대로 쓰지 않고 `파트너 기본정보`처럼 구별되게 쓴다.

반대로 **캔버스가 신경 쓰지 않아도 되는 것**도 분명히 해 둔다. 아래는 툴이 처리하므로 캔버스 마크업을 바꿀 이유가 없다.

- 접기/펼치기 스크립트가 `<h2>` 이후 형제들을 `div.sec-body`로 옮기는 것 — 앵커는 부모 체인을 쓰지 않아 영향받지 않고, 이 래퍼 자체는 앵커 대상에서 제외된다(원본 파일에 없는 런타임 생성 요소이므로).
- 코멘트가 가리키는 블록이 **접힌 섹션 안에 있는 경우** — 툴이 이동 전에 그 섹션을 펼친다.
- mermaid가 `<pre class="mermaid">`를 SVG로 바꾸는 것 — 지목 단위는 `<pre>`이고, 여기에 `id`가 있으면 렌더 전후와 무관하게 앵커가 유지된다.

## 화면(디자인) 작성 규칙

> ※ 이 섹션은 위 **A(화면이 있는 경우)**에만 적용된다. B(화면 없는 경우)의 파일명 규칙은 위 B 항목을 따른다.

**디자인 시스템 Reuse 원칙**: 통합캔버스를 만들 때와, 그 결과물을 바탕으로 실제 개발을 프롬프팅할 때 반드시 `design-system` 하위의 기존 컴포넌트를 참조·재사용한다. 이를 위해 1단계 산출물(통합캔버스)에 실제 컴포넌트명을 명시적으로 태깅해둔다 — 태깅이 없으면 2단계 개발 프롬프팅에서 AI가 비슷하게 생긴 컴포넌트를 새로 만들어버리기 쉽고, 애써 구축한 디자인 시스템이 재사용되지 않고 겉돌게 된다.

- **디자인 시스템 참조 디렉터리**: 화면 작업 대상에 따라 참조할 `design-system` 하위 디렉터리를 구분한다. `admin` 또는 `partner` 프로젝트 작업이면 `design-system/admin-partner`에서, 앱(사용자 대상) 프로젝트 작업이면 `design-system/app`에서 `design-system-app.md` 파일을 먼저 읽은 후 컴포넌트를 찾는다.
- **화면 제목**: `영어명 (한글명)` 형식으로 적는다. 예: `settlement-list (정산 내역 조회)`. 화면설명·UI 디스크립션 두 블록의 제목에도 동일한 이름을 그대로 써서 화면과 설명이 1:1로 짝지어지게 한다.
- **디스크립션 위치**: 디스크립션은 **유형에 따라 위치가 강제**된다. 아래 「디스크립션 유형과 위치」를 따른다.
- **번호 매핑**: 화면 내 기능 영역(조회 조건, 리스트, 버튼 등) 좌상단에 원형 번호 배지(1, 2, 3 …)를 붙이고, **UI 디스크립션(우측 패널)**에는 같은 번호의 순서 목록으로 각 영역을 설명한다. 실무 기획서·Figma 인스펙트에서 쓰는 "화면에 번호 찍고 번호별 설명" 방식을 그대로 따른다. 번호 목록은 우측에만 두고 화면설명에는 두지 않는다.
- **인터랙션**: 화면 안의 버튼·체크박스·탭·모달 등은 실제로 클릭했을 때 동작해야 한다(필터 적용, 모달 열기/닫기, 탭 전환에 따른 데이터 갱신 등). 정적 이미지가 아니라 살아있는 목업으로 만든다.
- **컴포넌트 태깅 — 화면 밖으로 뺀다**: 태깅은 아래 **두 곳에 병행** 기록하고, **화면 안에 눈에 보이는 텍스트로 노출하지 않는다.** 회색 주석 줄이 화면 공간을 차지하면 목업이 실제 화면처럼 읽히지 않는다.
  1. **실제 HTML 주석**: 요소 바로 앞에 `<!-- component: X(variant=...) | story: <스토리북 경로> (<컴포넌트 파일 경로>) -->`를 남긴다. 렌더링되지 않으므로 화면을 가리지 않으면서, 2단계 개발 프롬프팅에서 태깅을 grep으로 찾는 경로가 유지된다.
     - **컴포넌트 파일 경로를 반드시 포함한다 (필수).** 이것이 2단계 agile-issue와 캔버스를 잇는 **유일한 grep 연결선**이다. 캔버스는 스토리북 표기(`Inputs/Checkbox`)를 쓰고 애자일 이슈는 디렉터리 표기(`inputs/checkbox`)를 쓰므로 컴포넌트명만으로는 두 문서가 서로 검색되지 않는다. 경로(`src/components/inputs/checkbox/…`) 안에 이슈 쪽 표기가 부분 문자열로 들어 있어, 이 값이 있어야 **캔버스 태깅이 바뀌었을 때 영향받는 태스크를 찾아낼 수 있다.**
       - 이슈 쪽 대응물은 프론트·앱 태스크의 **UI 태그** `[ui: 화면1 ① inputs/checkbox]` 이고, 그 값의 출처가 이 주석이다(agile-issue-rule.md 「태스크 라인 형식」 참고). **여기서 경로를 빼면 화면이 바뀌었을 때 어느 태스크를 고쳐야 하는지 답할 수단이 없어진다.**
     - 스토리가 없으면 `| story: 없음 (<컴포넌트 파일 경로> — 스토리 파일 없음)`으로 적는다. 경로는 스토리 유무와 무관하게 항상 적는다.
     - 이 주석은 화면 안에 노출되지 않으므로 길어도 화면을 해치지 않는다. **길이를 이유로 줄이지 않는다.**
  2. **UI 디스크립션 항목에 병기**: 번호별 설명 끝에 그 영역이 쓰는 컴포넌트를 적는다. **사람이 읽는 표기는 여기 하나뿐이다.** 화면설명(하단)에는 컴포넌트를 적지 않는다. 표기는 아래 「스토리북 위치 명시」에 따라 **상세형이 원칙**이다.
  - 디자인 시스템에 없는 컴포넌트는 UI 디스크립션 병기에서 **색을 달리해** 기존 컴포넌트와 구분한다. (샘플 구현은 `class="comp proposed"` — 클래스명은 초기 명명이 남은 것이고, 의미는 "디자인 시스템 미보유" 표시다.)
  - ❌ 금지: `<div class="tag-note">&lt;!-- component: X --&gt;</div>` 처럼 이스케이프한 주석을 화면 안에 출력하는 방식.
- **스토리북 위치 명시 (필수)**: 태깅한 컴포넌트에 **스토리북 스토리가 존재하면 story id를 반드시 함께 적는다.** 컴포넌트명만 적으면 읽는 사람이 "이게 실물로 어떻게 생겼는지"를 확인할 경로가 없어, 결국 2단계에서 비슷한 것을 새로 만들게 된다. 태깅의 목적은 재사용이고, 재사용의 출발점은 실물 확인이다.
  - **표기(상세형)**: `<div class="tag-row"><span class="pair"><span class="tag">Header</span> <code>components-header--back-and-title</code></span>…</div>` — 컴포넌트명 + story id 쌍으로 적는다. story id는 스토리북 URL에 그대로 넣어 여는 값이다(`http://localhost:{포트}/?path=/story/{story id}`).
  - **위치를 어디서 확인하는가** — 아래 정본에서 **실재하는 값만** 가져온다. 스토리북 URL 규칙을 머릿속으로 추론해 그럴듯한 값을 지어내지 않는다. 트랙마다 정본이 다르다.

    | 트랙 | 정본(파일에 실재하는 값) | 태깅에 적는 값 | 포트 |
    |---|---|---|---|
    | 앱 (`design-system/app`) | `design-system/app/COMPONENT-CATALOG.md` 의 `story id` 열 | 그 story id 값 그대로 | 6007 |
    | 어드민·파트너 (`design-system/admin-partner`) | 카탈로그 파일이 없다. `src/**/*.stories.tsx` 의 `title` 메타 값(예: `title: 'Feedback/Modal'`) — 이 값이 grep으로 확인 가능한 유일한 실재 값이다 | `Feedback/Modal` (스토리북 사이드바 경로) + 파생 story id | 6008 |

  - **admin-partner의 story id는 파생값이다.** 어떤 파일에도 `feedback-modal--default` 라는 문자열은 없다. `title` 값과 export 이름을 스토리북 기본 규칙(둘 다 kebab-case로 바꿔 `--`로 잇는다)으로 변환한 결과다 — `.storybook/main.ts` 에 id 커스터마이즈가 없어 이 변환이 성립한다. 따라서 **반드시 적어야 하는 것은 `title` 값(스토리북 경로)이고**, story id는 URL로 바로 열기 위한 편의값으로 함께 적는다. `title` 값을 확인하지 않은 채 컴포넌트명만 보고 경로를 추측하지 않는다.
  - 요소 앞 HTML 주석의 형식은 위 「컴포넌트 태깅」 1번을 따른다. 예: `<!-- component: Modal | story: Feedback/Modal (src/components/feedback/modal/modal.stories.tsx) -->` — 이 경로가 검증 근거이면서 2단계와의 grep 연결선이다.
  - **스토리가 없으면** 컴포넌트명만 적고, 그 자리에 `스토리 없음`을 표시한다. 빈칸으로 두거나 있는 것처럼 적지 않는다. 정본을 확인할 수 없어 있는지 없는지조차 모르겠으면 지어내지 말고 **질문한다**(「형식을 지킬 수 없으면 질문한다」).
  - **간단형**(`<span class="comp">DateRangePicker · Checkbox</span>` — 컴포넌트명만 나열)은 그 화면에 쓰인 컴포넌트 **전부가 스토리 없음**일 때만 허용한다. 하나라도 스토리가 있으면 문서 전체를 상세형으로 통일한다. 상세형을 쓰면서 간단형을 **추가로 넣지 않는다**(같은 정보가 두 번 나온다).
  - 참고 예시 — **앱 트랙**: `canvas-app-restock-alert.html` (카탈로그의 실재 story id를 태그 칩에 병기하고 스토리북 URL 여는 방법까지 안내문에 적어둔 형태). **어드민·파트너 트랙**: `canvas-partner-settlement-detail.html` (HTML 주석에 `| story: Feedback/Modal (…/modal.stories.tsx)` 형태로 근거 파일까지 남기고, 스토리가 없는 `Table`은 `스토리 없음`으로 표시한 형태).
  - 디자인 시스템 미보유 항목은 애초에 컴포넌트가 없으므로 story id도 없다 — 아래 「디자인 시스템 미보유」 줄에서 다루고, 태깅 칩에 억지로 넣지 않는다.
- **디자인 시스템 미보유**: 전체 문서 상단에 한 줄로 뭉뚱그리지 않고, **화면마다 UI 디스크립션(우측 패널) 하단**에 "디자인 시스템 미보유" 줄을 둔다(컴포넌트 이야기이므로 화면설명이 아니라 UI 쪽이다). 기존 컴포넌트만으로 충분하면 `없음 — 사용한 컴포넌트 목록`을 적고, 표현이 안 되는 요소가 있으면 **어떤 요소가 무엇으로 덮이지 않는지 사실만** 적는다.
  - **이 줄은 "디자인 시스템에 추가하자"는 제안이 아니다.** 통합캔버스는 **없다는 사실만 보고**하고, 그 요소를 디자인 시스템에 편입할지 / 해당 화면 전용(page-local)으로 단발성 구현할지는 **여기서 결정하지 않는다.** 화면 하나에만 쓰이는 UI를 무조건 공용 컴포넌트로 만들면 디자인 시스템이 불필요하게 비대해지기 때문이다. 판단은 개발 착수 시점에 별도로 한다.
  - 미보유 항목은 아래 4가지로 **분류해서 적는다**(무엇이 없는지가 서로 다르고, 후속 판단도 달라진다):

    | 분류 | 의미 |
    |---|---|
    | `신규 필요` | 대체할 만한 컴포넌트가 아예 없다. 예: `신규 필요: SoldOutOverlay` |
    | `variant 값 추가 필요` | 컴포넌트는 있고 **값(variant) 이름만** 없다. 신규 컴포넌트가 아니다. 예: `variant 값 추가 필요: NoticeBox(CART_PRICE_CHANGED)` |
    | `참조 전용(page-local)` | 특정 화면이 소유한 로컬 컴포넌트라 공용 태깅 대상이 아니다. 예: `참조 전용(page-local): AllSelectHeader` |
    | `공용화 필요` | 다른 화면에 page-local로 이미 있고, 공용으로 끌어올릴 여지가 있다. 예: `공용화 필요 — my-page / PastHistoryGoodsItem` |

  - **있는 걸 임의로 새로 만들지 않는다.** 미보유로 적었다고 해서 곧바로 구현 대상이 되는 것은 아니다.
  - 미보유 영역은 번호 배지 색을 다르게(예: 주황) 하고 테두리를 점선 처리하는 정도로만 **화면 안에서 시각적으로** 구분한다. "신규 제안"·"미보유" 같은 문구 자체는 화면 콘텐츠 안에 텍스트로 넣지 않는다 — 실제 화면 카피와 혼동될 수 있다. 무엇이 미보유인지에 대한 설명은 번호로 연결된 UI 디스크립션 쪽에만 적는다.
- **파일명 규칙**: 화면 파일명은 `canvas-` 접두어 뒤에 대상 플랫폼(`admin` / `partner` / `app`)을 하이픈으로 연결하여 짓는다. 형식: `canvas-{platform}-{화면명}.html`. 예: `canvas-partner-settlement-list.html`, `canvas-admin-order-manage.html`, `canvas-app-home.html`.
- **참고 예시**: `canvas-partner-settlement-detail.html` — **「디스크립션 유형과 위치」·「스토리북 위치 명시」를 모두 반영한 규범 예시다.** 새 캔버스는 화면·디스크립션 구조를 이 파일 그대로 따른다.
  - ⚠️ **단, 이 파일에도 「플로우」는 없다** — 플로우 규칙 신설 이전에 작성됐다. **소제목 구성은 이 파일이 아니라 「통합캔버스 문서 구성」의 6개(플로우 포함)를 따르고**, 플로우는 「플로우 명세 수준」·「플로우 예시」를 따른다.
  - ⚠️ 나머지 `sample/` 캔버스(`-list` / `-summary` / `canvas-app-restock-alert`)는 **규칙 신설 이전에 작성**되어 화면설명(`.screen-note`) 블록이 없고 로직 설명이 우측 패널에 섞여 있다. 화면 구성·인터랙션은 참고해도 되지만, **디스크립션 배치는 반드시 `-detail` 쪽을 따른다.**

## 디스크립션 유형과 위치

> ※ 이 섹션은 **A(화면이 있는 경우)**에만 적용된다. B(화면 없는 경우)는 화면이 없으므로 디스크립션 자체를 쓰지 않는다.

디스크립션은 성격이 다른 두 종류가 섞여 있다 — **"이 화면이 무엇이고 어떤 규칙으로 동작하는가"**(기획·로직)와 **"화면의 이 영역은 무엇인가"**(UI). 둘을 한 덩어리에 쓰면 기획 검토자는 UI 나열 사이에서 정책을 찾아야 하고, 개발자는 정책 문장 사이에서 컴포넌트를 찾아야 한다. **유형에 따라 위치를 강제한다.**

| 유형 | 무엇을 쓰는가 | 어디에 쓰는가 | 블록 |
|---|---|---|---|
| **화면설명** | 페이지 자체에 대한 설명, 비즈니스 규칙·로직·정책, 데이터 출처(**업무 기준** — 어떤 업무 데이터를 근거로 표시하는가. 엔드포인트·응답 필드 같은 전송 계층이 아니다)와 계산식, 진입/이탈 경로, 권한, 예외·경계 처리 | **화면 바로 아래에 실제로 보이게** (숨기지 않는다) | `.screen-note` |
| **UI 디스크립션** | 번호 배지로 지목한 화면 영역별 설명, 컴포넌트 태깅(+ story id), 인터랙션 동작, 디자인 시스템 미보유 | **우측 고정 플로팅 패널** (토글로 접힘) | `.screen-desc` |

### 화면설명 ≠ 유저스토리 (중복 방지)

화면설명은 **세 번째 요구사항 저장소가 아니다.** 유저스토리와 경계를 지키지 않으면 같은 내용이 두 곳에 적히고, 나중에 한쪽만 고쳐져 2단계에서 어느 쪽이 정본인지 알 수 없게 된다.

| | 무엇을 담는가 | 형식 |
|---|---|---|
| **유저스토리** | 사용자·시스템의 **행동 시나리오** — "누가 무엇을 하면 무엇이 일어나는가" | Given-When-Then 단위 |
| **화면설명** | 그 화면에 고정된 **규칙 자체** — 계산식, 데이터 출처(업무 기준), 권한, 표기 기준, 경계값. 행동 단위로 쪼개지지 않는 것 | 글머리 목록 |

예: `최종 정산액 = 상품 판매액 − 플랫폼 수수료 ± 조정 금액` 은 계산식이므로 화면설명. `Given 정산 건이 있고, When 상세를 열면, Then 산출 근거가 표시된다` 는 행동이므로 유저스토리. 화면설명에 GWT를 복사해 넣지 않는다.

### 어느 쪽에 쓸지 판정하는 법

문장 하나를 두고 아래 세 질문을 순서대로 던진다. 애매하다는 느낌으로 정하지 말고 이 테스트로 정한다.

1. **번호 배지에 걸리는가?** — 화면의 특정 영역(1번, 2번 …)을 지목해야만 의미가 통하면 → **UI 디스크립션**.
2. **행동 시나리오로 쓸 수 있는가?** — `Given … When … Then …` 형태로 자연스럽게 써지면 → **유저스토리**(화면설명에 중복해서 적지 않는다).
3. **UI를 전면 재설계해도 그 문장이 그대로 살아남는가?** — 모달을 페이지로 바꾸고 버튼 배치를 다 갈아엎어도 여전히 참이면 → **화면설명**. (계산식·권한·데이터 규칙·표기 기준은 대부분 여기 해당한다.)

두 개 이상에 걸리는 문장은 **한 문장에 여러 유형이 섞인 것**이다. 문장을 쪼개서 각각의 자리로 보낸다.

**쪼개기 예시** — `canvas-partner-settlement-detail.html`의 2번 항목:

```
❌ 섞인 원문 (전부 우측 패널에 있었다)
2 정산 상세 모달 — 파트너명과 산출 근거(상품 판매액 / 플랫폼 수수료 / 조정 금액 /
  최종 정산액)를 InfoField로 나열한다. 닫기 버튼 · 헤더 ✕ · 배경 클릭 · ESC
  4가지 경로로 닫히며, 모달 내부 클릭으로는 닫히지 않는다.
  보류 건은 최종 정산액에 보류임을 함께 표기한다.
```


### 화면설명 작성 규칙

- **위치**: 화면 목업(`.screen-mock`) 바로 아래, `.screen-desc`와 **형제 블록**으로 둔다. `.screen-note`는 **숨기지 않는다** — 화면을 스크롤하며 읽을 때 그 화면의 규칙이 바로 밑에 붙어 있어야 한다.
- **제목**: `화면설명 — {영어명} ({한글명})`. 화면 제목과 글자 그대로 같은 이름을 쓴다. "페이지 설명"·"기능 설명" 등 다른 말로 바꾸지 않는다.
- **형식**: 번호 목록이 아니라 **글머리 목록**으로 쓴다. 번호는 UI 영역 지목 전용이므로 화면설명에서 번호를 쓰면 UI 디스크립션과 혼동된다.
- **컴포넌트명·story id를 적지 않는다.** 화면설명에 컴포넌트가 등장하면 그 문장은 UI 디스크립션으로 가야 할 문장이다.
- **백엔드 구현을 정의하지 않는다 (필수).** 아래 항목은 화면설명에 적지 않는다.
  - API 엔드포인트·HTTP 메서드·요청 파라미터·요청/응답 body·응답 필드명
  - 상태 enum 값, DB 테이블·컬럼·스키마, 서버 클래스·메서드명, 서버 검증 애너테이션
  - "이렇게 부르면 될 것 같다" 수준의 **명명 제안**, "이런 API가 필요하다"는 **신설 제안**
  - **왜**: 통합캔버스는 화면과 그 화면에 고정된 업무 규칙을 정의하는 문서이고, 백엔드 계약은 이 문서가 정의할 권한이 없는 영역이다. 지어낸 엔드포인트·필드명이 캔버스에 한 줄 들어가면 2단계 agile-issue의 태스크·테스트가 그 전제 위에서 파생되고, 실제 백엔드 계약이 확정되는 순간 전부 되돌려야 한다(「형식을 지킬 수 없으면 질문한다」와 같은 이유다).
  - **옮길 곳이 따로 있는 것이 아니다.** 컴포넌트명은 UI 디스크립션이라는 목적지가 있지만, 백엔드 계약은 **1단계 통합캔버스 안에 자리가 없다** — 화면설명도, UI 디스크립션도, B유형의 4개 소제목도 아니다. 다른 블록으로 옮기지 말고 **적지 않는다.** 백엔드 동작을 다뤄야 하는 작업이면 그것은 B유형 캔버스의 **유저스토리·플로우**로 쓸 일이지, 화면설명에 계약을 적을 일이 아니다.
  - **전제 명시로도 우회할 수 없다.** `전제(확정 필요) — 명명 제안이다` 처럼 단서를 달아도 지어낸 계약은 지어낸 계약이다. 「형식을 지킬 수 없으면 질문한다」의 전제 명시는 **기획 정책**의 공백을 메우는 장치이지, 백엔드 계약을 창작하는 허가가 아니다. 화면 동작에 백엔드 계약이 꼭 필요하면 지어내지 말고 **질문한다.**
  - **하위 블록을 만들어 우회하지 않는다.** `.screen-note` 안에 `note-annex` 같은 임의의 블록·표를 추가해 API 계약표·DB 매핑표를 넣는 것도 같은 위반이다(「형식을 임의로 바꾸기」에 해당). 화면설명의 형식은 글머리 목록 하나다.
  - ✅ **적어도 되는 것** — 업무 기준의 데이터 출처와 표기 규칙. 예: `정산 금액은 확정된 정산 데이터를 기준으로 표시한다`, `목록은 심사 상태 6종을 탭으로 나눠 보여준다`. ❌ `GET /partner/partner-reviews 로 조회한다`, `응답 필드는 reviewSubmittedAt 으로 제안한다`.
- 근거 없는 정책을 채우지 않는다. 로직 칸이 비었다는 것은 대개 기획에 그 정책이 없다는 뜻이므로, 지어내지 말고 **질문한다**(「형식을 지킬 수 없으면 질문한다」).

### UI 디스크립션(우측 패널) 규칙

기존 플로팅 패널 구조를 그대로 유지한다. 바뀐 것은 **패널에 담기는 내용이 UI로 한정**된다는 점뿐이다.

- **제목**: `UI 디스크립션 — {영어명} ({한글명})`. 그냥 `디스크립션 — …` 으로 두지 않는다 — "디스크립션"은 두 유형을 아우르는 상위 이름이라, 블록 제목이 그 이름이면 로직 설명까지 이 블록에 담기게 된다.
- **마크업 원본은 화면 아래 `.screen-desc` 블록에 그대로 둔다.** 패널은 그 블록을 복제해 보여주기만 하고, 원본은 CSS로 숨긴다(`.screen-desc { display: none }`). 작성·리뷰 대상은 언제나 화면 아래의 원본이며, 패널은 표시 장치일 뿐이다.
- **패널은 `.screen-desc`만 복제한다.** `.screen-note`(화면설명)는 복제 대상이 아니다 — 복제하면 화면설명이 하단과 우측에 두 번 나온다.
- **스크롤 연동**: `IntersectionObserver`로 뷰포트에서 가장 많이 보이는 화면 블록을 감지해, 패널 내용을 그 화면의 UI 디스크립션으로 자동 교체한다. 패널 헤더에 현재 화면명(`화면 N · 화면명`)을 표시한다.
- 문서 전체에 패널은 **1개**만 둔다. 화면마다 패널을 만들지 않는다.

```
[유저스토리 작성 규칙]
유저스토리는 스토리 이름 + Given-When-Then(GWT) 시나리오로 작성해줘. 스토리 이름은
단순 작업명이 아니라 누가/무엇을/왜 하려는지가 드러나게 짓고, 본문은
`Given <사전 조건>, When <행동>, Then <기대 결과>` 형식으로 써줘. 정상/예외 등
조건 분기가 있으면 GWT 시나리오를 나눠서 적어줘. 예외까지 망라한 상세 수락 기준과
성공/실패 테스트는 이 문서에 넣지 말고 2단계(agile-issue)에서 이 GWT를 상세화할 거야.

스토리마다 GWT 바로 아래에 「동작 순서」 블록을 반드시 넣어줘 (예외 없음).
- GWT를 쉬운 말로 단계적으로 다시 쓴 거야. 버그 재현 경로처럼 번호 목록으로,
  한 줄에 한 동작씩 `~합니다` 로 끝나게 써줘. 마지막 줄은 확인 결과로 끝내줘.
  예) 1. 검수 및 결과보고 팝업에 접근합니다.
      2. 검수사진 및 수령 사진 첨부를 시도합니다.
      3. 예시로 A, B, C 3장의 이미지를 첨부합니다.
      4. A, B, C 파일이 첨부됨을 확인할 수 있습니다.
- GWT 시나리오 1개당 목록 1개야. 시나리오가 3개면 목록도 3개. 하나로 합치지 마
  (합치면 정상·예외가 섞여 분기별 결과가 사라진다).
  시나리오가 2개 이상이면 목록마다 무슨 경우인지 라벨을 <p class="steps-case"> 로 붙여줘.
- Given 은 그 상태에 이르는 동작이 있으면 첫 단계로 풀고(예: "정산 내역 목록 화면에
  접근합니다"), 사용자가 할 수 있는 동작이 아니면 "~인 상태에서 시작합니다"로 적어줘.
- GWT에 없는 단계·조건·화면을 여기서 만들지 마. 같은 내용의 다른 표현일 뿐이야.
  풀어 쓸 근거가 부족하면 지어내지 말고 물어봐.
- <div class="story-steps" id="steps-{스토리명}"> 안에 <h5>동작 순서 — {스토리명}</h5> 과
  <ol> 로 넣어줘.

[플로우 작성 규칙 — 필수]
유저스토리 다음, 화면(디자인) 앞에 `플로우` 소제목을 두고 이 에픽의 흐름을
mermaid로 그려줘.
- `<pre class="mermaid">` 안에 mermaid 소스를 평문 그대로 넣어줘.
  렌더된 이미지나 SVG로 대체하지 마 (캔버스와 이슈를 대조해야 하고,
  2단계 agile-issue 에픽 흐름도가 이 소스를 그대로 계승한다).
- 기본은 flowchart TD. 시간 순서·주체 간 주고받음이 핵심이면 sequenceDiagram도 돼.
- 이 캔버스가 소유한 에픽 1개의 흐름만 그려. 다른 에픽은 진입/이탈 노드 하나로만 표시하고
  그 안을 펼치지 마.
- 화면에 해당하는 노드에는 `화면 N`을 병기해줘. 예: A[화면 1 · settlement-list<br/>정산 내역 목록]

  네트워크가 없으면 소스 텍스트로 보이므로, 노드 이름은 알아볼 수 있게 지어줘.
- 노드와 분기는 바로 위 유저스토리 GWT·에픽 범위에 근거가 있는 것만 그려.
  플로우가 새 분기·새 정책을 만들어내면 안 돼. 근거 없으면 그리지 말고 질문해줘.

[소제목 접기/펼치기 — 필수]
모든 h2 소제목을 클릭하면 그 아래 내용이 접히고 다시 펼쳐지게 해줘.
- 기본은 전부 펼침. 접힌 채로 열리게 만들지 마.
- 섹션마다 래퍼 div를 손으로 감싸지 말고, 문서 하단 스크립트가 h2부터 다음 h2 직전까지를
  자동으로 묶게 해줘. 스크립트는 문서에 딱 1개, mermaid 로더보다 앞에 둬.
- h2에 role="button" · tabindex="0" · aria-expanded 를 붙이고 Enter/Space로도 토글되게.
  ▾/▸ 표시는 CSS ::after 로 붙이고 화면 텍스트로 넣지 마.
- 화면(디자인)이 접히면 우측 UI 디스크립션 패널도 함께 숨겨줘 —
  IntersectionObserver 대상(.screen-block)이 사라져 패널이 옛 화면을 띄운 채 남는다.
  (구체 구현은 one-canvas-rule.md 「소제목 접기/펼치기」의 스크립트를 그대로 써도 돼)

[수정일 — 필수]
<title> 바로 다음에 이 캔버스의 작성 시각을 넣어줘.
  <meta name="canvas-updated-at" content="2026-08-12T14:30:00+09:00">
ISO 8601 + 오프셋 형식이고, 날짜만 적지 마(시:분까지).
앞으로 이 캔버스를 고칠 때마다 이 값을 그 시각으로 갱신한다
(one-canvas-rule.md 「수정하면 수정일을 남긴다」).
예시 캔버스에 적힌 날짜를 그대로 복사하지 말고 지금 시각으로 넣어줘.

[확정 표기 — 넣지 마]
새로 만드는 캔버스는 **미확정**이야. canvas-status · canvas-confirmed-at 같은 확정 meta나
문서 상단 확정 배지를 넣지 마 — 확정은 이 캔버스에서 애자일 이슈를 최초 생성할 때
기록되는 값이야(one-canvas-rule.md 「확정 상태 기록」).
참고용으로 준 예시 캔버스에 확정 표기가 보이더라도 그것까지 따라 복사하지 마.

[블록 id — 필수]
코멘트가 블록에 계속 붙어 있으려면 리뷰 대상 블록에 id가 있어야 해. 아래에 id를 붙여줘.
- h2 소제목 → sec-domain · sec-ref · sec-epic · sec-story · sec-flow · sec-screen
- 화면 블록 .screen-block → screen-{화면 영어명}
- 화면설명 .screen-note → note-{화면 영어명}
- UI 디스크립션 .screen-desc → desc-{화면 영어명}
- 플로우 pre.mermaid → flow-{도메인}
- 표 table → table-epic · table-domain 처럼 무엇의 표인지 드러나게
id는 문서 안에서 유일해야 하고, 의미에서 따와야 해(순번 남발 금지).
반대로 data-block 같은 코멘트 전용 속성은 절대 넣지 마 — 앵커는 툴이 계산하고,
원본에 심으면 리뷰할 때마다 캔버스 파일이 수정돼 작성자와 충돌이 난다.

[디스크립션 유형 분리 — 필수]
디스크립션을 한 덩어리로 쓰지 마. 유형에 따라 위치를 나눠줘.

(1) 화면설명 — 화면 목업 바로 아래 `.screen-note` 블록. 숨기지 말고 실제로 보이게.
    제목은 `화면설명 — {영어명} ({한글명})` 그대로 쓴다.
    담을 내용: 페이지 자체에 대한 설명, 비즈니스 규칙·로직·정책, 계산식, 데이터 출처,
    진입/이탈 경로, 권한, 예외·경계 처리.
    글머리 목록으로 쓰고, 번호 목록은 쓰지 마(번호는 UI 영역 지목 전용).
    컴포넌트명과 story id는 여기 적지 마.
    백엔드 구현은 정의하지 마 — API 엔드포인트·요청/응답 body·응답 필드명·상태 enum 값·
    DB 테이블/컬럼·서버 클래스명을 적지 말고, "이렇게 부르면 될 것 같다"는 명명 제안이나
    "이런 API가 필요하다"는 신설 제안도 하지 마. 통합캔버스가 정의할 영역이 아니야.
    `전제(확정 필요)` 같은 단서를 달아도 안 되고, .screen-note 안에 별도 블록이나
    API 계약표·DB 매핑표를 추가해서 우회하지도 마. 화면설명 형식은 글머리 목록 하나다.
    「데이터 출처」는 업무 기준으로만 써 — "확정된 정산 데이터를 기준으로 표시한다"는 O,
    "GET /partner/settlements 로 조회한다"는 X.
    화면 동작에 백엔드 계약이 꼭 필요하면 지어내지 말고 나에게 질문해줘.

(2) UI 디스크립션 — `.screen-desc` 블록. 우측 고정 플로팅 패널에 띄우고 토글로 접었다 펼 수 있게.
    제목은 `UI 디스크립션 — {영어명} ({한글명})` 로 써줘. 그냥 `디스크립션` 이라고 쓰지 마.
    원본은 화면 아래에 두되 CSS로 숨기고, 패널이 복제해서 보여준다.
    스크롤에 따라 현재 보는 화면의 UI 디스크립션으로 자동 교체(IntersectionObserver).
    패널은 `.screen-desc`만 복제하고 `.screen-note`는 복제하지 마(두 번 나온다).
    담을 내용: 번호 배지로 지목한 영역별 설명, 컴포넌트 태깅 + story id,
    인터랙션 동작, 디자인 시스템 미보유.

어디에 쓸지 애매하면 이 테스트로 정해줘:
- 번호 배지가 붙은 특정 영역을 지목해야 의미가 통한다 → UI 디스크립션
- Given/When/Then 형태로 자연스럽게 써진다 → 유저스토리 (화면설명에 중복해서 쓰지 마)
- UI를 전면 재설계해도 그 문장이 그대로 참이다 → 화면설명
- 두 개 이상 걸리면 한 문장에 여러 유형이 섞인 것이니 문장을 쪼개서 각각 보내줘.
```

```
[유저스토리 작성 규칙]
유저스토리는 스토리 이름 + Given-When-Then(GWT) 시나리오로 작성해줘. 화면이 없는
경우이므로 사용자 대신 시스템/배치가 주체가 되도록, GWT의 When도 시스템 이벤트가
주체가 되게 써줘. 스토리 이름은 단순 작업명이 아니라 누가(또는 무엇이)/무엇을/왜
하려는지가 드러나게 지어줘. 예외까지 망라한 상세 수락 기준과 성공/실패 테스트는 이
문서에 넣지 말고 2단계(agile-issue)에서 이 GWT를 상세화할 거야.

스토리마다 GWT 바로 아래에 「동작 순서」 블록을 반드시 넣어줘 (예외 없음).
- GWT를 쉬운 말로 단계적으로 다시 쓴 거야. 버그 재현 경로처럼 번호 목록으로,
  한 줄에 한 동작씩 `~합니다` 로 끝나게 써줘. 마지막 줄은 확인 결과로 끝내줘.
  화면이 없으므로 주체는 시스템·배치야.
  예) 1. 정산 배치가 반품 확정 이벤트를 감지합니다.
      2. 해당 정산 건의 금액을 재계산합니다.
      3. 재계산된 금액으로 정산 데이터가 갱신됨을 확인할 수 있습니다.
- GWT 시나리오 1개당 목록 1개야. 시나리오가 2개 이상이면 목록마다 무슨 경우인지
  라벨을 <p class="steps-case"> 로 붙여줘. 하나로 합치지 마.
- GWT에 없는 단계·조건을 여기서 만들지 마. 같은 내용의 다른 표현일 뿐이야.
  풀어 쓸 근거가 부족하면 지어내지 말고 물어봐.
- <div class="story-steps" id="steps-{스토리명}"> 안에 <h5>동작 순서 — {스토리명}</h5> 과
  <ol> 로 넣어줘.

[플로우 작성 규칙 — 필수]
유저스토리 다음(화면이 없으므로 문서 마지막)에 `플로우` 소제목을 두고
이 에픽의 흐름을 mermaid로 그려줘.
- `<pre class="mermaid">` 안에 mermaid 소스를 평문 그대로 넣어줘.
  렌더된 이미지나 SVG로 대체하지 마 (캔버스와 이슈를 대조해야 하고,
  2단계 agile-issue 에픽 흐름도가 이 소스를 그대로 계승한다).
- 화면이 없으므로 노드의 주체는 사용자가 아니라 **시스템 이벤트·배치 단계·상태 전이**야.
  트리거(스케줄/이벤트) → 처리 단계 → 성공/실패 분기 → 결과(저장·알림·재시도) 순으로 그려줘.
- 기본은 flowchart TD. 여러 시스템이 주고받는 흐름이면 sequenceDiagram도 돼.
- 이 캔버스가 소유한 에픽 1개의 흐름만 그려. 다른 에픽은 진입/이탈 노드 하나로만 표시해.
- 문서 하단에 mermaid CDN 로더를 딱 1개만 넣어줘:
  <script type="module">
    import mermaid from 'https://cdn.jsdelivr.net/npm/mermaid@11/+esm';
    mermaid.initialize({ startOnLoad: true, theme: 'neutral' });
  </script>
  네트워크가 없으면 소스 텍스트로 보이므로, 노드 이름은 알아볼 수 있게 지어줘.
- 노드와 분기는 바로 위 유저스토리 GWT·에픽 범위에 근거가 있는 것만 그려.
  플로우가 새 분기·새 정책을 만들어내면 안 돼. 근거 없으면 그리지 말고 질문해줘.

[소제목 접기/펼치기 — 필수]
모든 h2 소제목을 클릭하면 그 아래 내용이 접히고 다시 펼쳐지게 해줘.
- 기본은 전부 펼침. 접힌 채로 열리게 만들지 마.
- 섹션마다 래퍼 div를 손으로 감싸지 말고, 문서 하단 스크립트가 h2부터 다음 h2 직전까지를
  자동으로 묶게 해줘. 스크립트는 문서에 딱 1개, mermaid 로더보다 앞에 둬.
- h2에 role="button" · tabindex="0" · aria-expanded 를 붙이고 Enter/Space로도 토글되게.
  ▾/▸ 표시는 CSS ::after 로 붙이고 화면 텍스트로 넣지 마.
  (구체 구현은 one-canvas-rule.md 「소제목 접기/펼치기」의 스크립트를 그대로 써도 돼)

[수정일 — 필수]
<title> 바로 다음에 이 캔버스의 작성 시각을 넣어줘.
  <meta name="canvas-updated-at" content="2026-08-12T14:30:00+09:00">
ISO 8601 + 오프셋 형식이고, 날짜만 적지 마(시:분까지).
앞으로 이 캔버스를 고칠 때마다 이 값을 그 시각으로 갱신한다
(one-canvas-rule.md 「수정하면 수정일을 남긴다」).
예시 캔버스에 적힌 날짜를 그대로 복사하지 말고 지금 시각으로 넣어줘.

[확정 표기 — 넣지 마]
새로 만드는 캔버스는 **미확정**이야. canvas-status · canvas-confirmed-at 같은 확정 meta나
문서 상단 확정 배지를 넣지 마 — 확정은 이 캔버스에서 애자일 이슈를 최초 생성할 때
기록되는 값이야(one-canvas-rule.md 「확정 상태 기록」).
참고용으로 준 예시 캔버스에 확정 표기가 보이더라도 그것까지 따라 복사하지 마.

[블록 id — 필수]
코멘트가 블록에 계속 붙어 있으려면 리뷰 대상 블록에 id가 있어야 해. 아래에 id를 붙여줘.
- h2 소제목 → sec-domain · sec-ref · sec-epic · sec-story · sec-flow
- 플로우 pre.mermaid → flow-{도메인}
- 표 table → table-epic · table-domain 처럼 무엇의 표인지 드러나게
id는 문서 안에서 유일해야 하고, 의미에서 따와야 해(순번 남발 금지).
반대로 data-block 같은 코멘트 전용 속성은 절대 넣지 마 — 앵커는 툴이 계산하고,
원본에 심으면 리뷰할 때마다 캔버스 파일이 수정돼 작성자와 충돌이 난다.

[형식을 못 지킬 때 — 필수]
형식·항목을 추측으로 채우지 마. 요구사항이나 기존 문서에 근거가 없어서
지어내야 하는 항목이 나오면 멈추고 나에게 질문해줘.
- 빈칸을 그럴듯한 문장으로 채우거나, TBD만 적고 넘어가거나,
  못 채우는 항목을 통째로 생략하거나, 형식을 임의로 바꾸는 건 금지.
- 막힌 그 항목만 질문하고 근거 있는 나머지는 계속 작성해도 돼.
- 전제를 깔고 진행해야 하면 전제를 문서에 명시해줘.
- 근거가 있어서 스스로 판단한 항목이 애매했다면 `(근거: …)`를 같이 적어줘.

[파일 위치·파일명]
`one-canvas/<기획-건>/` 폴더 안에 만들어줘. 화면 있는 캔버스와 같은 기획 건이면
같은 폴더에 넣고 별도 폴더로 분리하지 마. `sample/` 하위에는 만들지 마.
파일명은 canvas-{platform}-{에픽명}-noscreen.html 형식으로 지어줘.
예: one-canvas/partner-settlement/canvas-partner-settlement-batch-noscreen.html
```

## 통합캔버스 리뷰 체크리스트

기획자가 AI 프롬프트로 통합캔버스를 생성·수정한 뒤, 아래 체크리스트로 이 문서(one-canvas-rule.md) 기준 미비 사항을 점검한다. 각 항목은 위 규칙 섹션과 1:1로 대응한다.

- [ ] **근거 없는 내용이 없는가**: 요구사항·기존 문서에 근거가 없는데 그럴듯하게 채워 넣은 항목이 없는가? `TBD`/`미정`만 적힌 채 질문 없이 남은 항목은 없는가? 못 채워서 통째로 생략된 항목·소제목은 없는가? 전제를 깔고 쓴 부분에 전제가 명시돼 있는가? (「형식을 지킬 수 없으면 질문한다」 참고)
- [ ] **문서 구성**: 화면 유무에 맞게 A(6개: 도메인/에픽/유저스토리/플로우/화면(디자인)/디스크립션(화면당)) 또는 B(4개: 도메인/에픽/유저스토리/플로우) 소제목만 있는가? **순서까지 맞는가**(특히 플로우가 유저스토리와 화면 사이인가)? "요구사항 정의"라는 별도 소제목이 남아있지 않은가?
- [ ] **플로우**: 「플로우」 소제목이 **유저스토리 다음, 화면(디자인) 앞**에 있는가(B는 문서 마지막)? mermaid **소스가 평문**으로 `<pre class="mermaid">`에 들어 있는가(렌더 이미지·SVG·외부 파일로 대체되지 않았는가)? 다이어그램이 이 캔버스의 **에픽 1개 범위**인가(다른 에픽 내부까지 펼치지 않았는가)? 노드·분기가 **에픽 범위·유저스토리 GWT에 근거**하는가 — 플로우가 문서에 없는 분기·정책을 새로 만들지 않았는가? mermaid CDN 로더가 문서에 **1개만** 있는가? (A라면 화면 노드에 `화면 N`이 병기됐는가 / B라면 주체가 시스템·배치인가)
- [ ] **코멘트 앵커**: 코멘트 전용 태깅(`data-block` 등)이 원본에 심겨 있지 **않은가**? 리뷰가 오래 붙는 단위(`<h2>` 소제목·`.screen-block`·`.screen-note`·`.screen-desc`·플로우 `<pre class="mermaid">`)에 **의미 기반 `id`가 있는가**? 기존 `id`를 문구 정리 과정에서 **바꾸거나** 삭제된 블록의 `id`를 **다른 블록에 재사용**하지 않았는가? 소제목·표 제목이 문서 안에서 **똑같이 반복**되지 않는가? (「코멘트가 블록에 붙어 있으려면」 참고)
- [ ] **소제목 접기/펼치기**: 모든 `<h2>`가 클릭으로 접히고 펼쳐지는가? 문서를 열었을 때 **전부 펼쳐진 상태**인가(기본 접힘으로 만들어 항목 누락이 가려지지 않는가)? 토글 스크립트가 문서에 **1개만** 있고 mermaid 로더보다 **앞**에 있는가? (A만) 「화면(디자인)」을 접었을 때 **우측 UI 디스크립션 패널이 함께 사라지는가** — 사라진 화면의 디스크립션을 띄운 채 남아 있지 않은가? `aria-expanded`·키보드 토글이 있는가?
- [ ] **도메인**: kebab-case 영문명 + 한글명 병기 형식(`settlement (정산)`)을 지켰는가? 하나의 도메인만 기록했는가?
- [ ] **참고 자료** (있는 경우): `자료명 — 링크 — 한 줄 설명` 형식을 지켰는가? 관련 자료가 없는데도 빈 섹션이 남아있지 않은가?
- [ ] **에픽**: 문서에 에픽이 **1개만** 있는가(2개 이상이면 캔버스 파일을 분리해야 함)? 목적 / 주요 범위(In-Scope) / 제외 범위(Out-of-Scope) / 완료 기준 4항목이 모두 있는가?
- [ ] **유저스토리**: 스토리 이름 + Given-When-Then(GWT) 형식으로 쓰였는가(`Given/When/Then`)? 스토리 이름에 누가/무엇을/왜가 드러나는가? 정상/예외 분기가 GWT 시나리오로 분리돼 있는가? 문서에 없는 조건·정책을 GWT가 지어내지 않았는가? (B라면 사용자 대신 시스템/배치가 주체인가?)
- [ ] **동작 순서** (규칙 신설 이전에 작성된 캔버스에는 소급 적용하지 않는다 — 「동작 순서」 참고): **스토리마다 빠짐없이** 「동작 순서」 블록이 있고 **GWT 시나리오 개수와 목록 개수가 1:1로 맞는가**? 번호 목록으로 한 줄에 한 동작씩, `~합니다` 종결로 쓰였는가? **마지막 줄이 확인 결과**로 끝나는가? **GWT에 없는 단계·조건을 새로 만들어 넣지 않았는가** — 쉬운 말로 푸는 과정에서 "당연히 이렇게 되겠지"를 채운 곳은 없는가? GWT를 고쳤는데 동작 순서가 옛 내용으로 남아 있지 않은가? `id`가 `steps-<스토리명>` 형식인가? (「동작 순서」 참고)
- [ ] **(A만) 화면(디자인)**: 화면 제목이 `영어명 (한글명)` 형식인가? UI 디스크립션이 우측 플로팅 패널에 뜨고 토글로 접히는가? 스크롤에 따라 현재 화면 디스크립션으로 교체되는가? 번호 매핑이 1:1로 대응하는가? 버튼/체크박스/탭/모달 등이 실제로 동작하는가(정적 이미지로 남아있지 않은가)? 요소마다 실제 HTML 주석 `<!-- component: X -->` 태깅이 빠짐없이 있고, UI 디스크립션 항목에도 컴포넌트가 병기돼 있는가? 화면 안에 태깅이 보이는 텍스트로 노출돼 있지는 않은가?
- [ ] **(A만) 디스크립션 유형 분리**: 화면마다 `.screen-note`(화면설명)와 `.screen-desc`(UI 디스크립션)가 **둘 다** 있는가? 화면설명 블록이 화면 아래에 **실제로 보이는가**(숨겨져 있거나 우측 패널에 복제되고 있지 않은가)? 두 블록의 제목이 각각 `화면설명 — {영어명} ({한글명})` / `UI 디스크립션 — {영어명} ({한글명})` 인가(우측 블록 제목이 `디스크립션 — …` 으로 남아 있지 않은가)? **정책·계산식·권한·예외 처리 같은 로직 설명이 우측 패널에 섞여 있지 않은가?** 반대로 **번호 배지로 지목한 영역 설명·컴포넌트 태깅이 화면설명에 섞여 있지 않은가?** 화면설명이 번호 목록으로 쓰여 있지 않은가? **유저스토리 GWT가 화면설명에 복사돼 중복되지 않았는가?** (「디스크립션 유형과 위치」 판정 테스트 참고)
- [ ] **(A만) 화면설명에 백엔드 계약이 없는가**: API 엔드포인트·HTTP 메서드·요청/응답 body·응답 필드명·상태 enum 값·DB 테이블/컬럼·서버 클래스명이 화면설명에 적혀 있지 않은가? "명명 제안"·"이런 API가 필요하다" 같은 **제안**이 섞여 있지 않은가? `전제(확정 필요)` 단서를 달아 우회한 곳은 없는가? `.screen-note` 안에 규칙에 없는 하위 블록(API 계약표·DB 매핑표 등)을 만들어 넣지 않았는가 — 화면설명은 글머리 목록 하나인가? 「데이터 출처」가 엔드포인트가 아니라 **업무 기준**으로 쓰여 있는가? (「화면설명 작성 규칙」 참고)
- [ ] **(A만) 스토리북 위치**: 태깅한 컴포넌트마다 스토리북 위치가 명시돼 있는가? 그 값이 파일에서 grep으로 확인되는 실재 값인가 — app은 `COMPONENT-CATALOG.md` 의 `story id` 열 값, admin-partner는 `src/**/*.stories.tsx` 의 `title` 값(예: `Feedback/Modal`)이 문서에 그대로 있는가? 컴포넌트명만 보고 추측한 경로가 아닌가? 스토리가 없는 컴포넌트는 `스토리 없음`으로 표시돼 있는가(빈칸으로 방치되지 않았는가)? 한 문서 안에서 상세형/간단형이 섞여 있지 않은가?
- [ ] **(A만) 디자인 시스템 미보유**: 화면마다 UI 디스크립션 하단에 "디자인 시스템 미보유" 줄이 있는가(문서 상단에 한 번만 뭉뚱그리지 않았는가)? 없으면 "없음 — 사용한 컴포넌트 목록"으로 채워져 있는가? 미보유 항목이 4분류(신규 필요/variant 값 추가 필요/참조 전용(page-local)/공용화 필요)로 적혀 있는가? **디자인 시스템 편입을 권하는 문구가 섞여 있지는 않은가**(캔버스는 사실 보고까지만)?
- [ ] **디자인 시스템 참조**: admin/partner 작업은 `design-system/admin-partner`, app 작업은 `design-system/app` 컴포넌트만 참조했는가? 실제로 없는 컴포넌트를 임의로 만들어 쓰지 않았는가?
- [ ] **확정 표기** (`sample/` 규범 예시는 이 항목 제외 — 「새로 만드는 캔버스는 미확정이다」 참고): 이 캔버스에서 파생된 애자일 이슈가 있는데 확정 meta가 빠져 있지 않은가(반대로 이슈가 없는데 확정으로 적혀 있지 않은가)? meta가 `<title>` **바로 다음**에 있는가 — `<style>` 뒤로 밀려 앞머리 스캔에서 벗어나지 않았는가? 배지가 `<div>`로 들어가 코멘트 앵커 인덱스를 밀어내고 있지 않은가? 확정 시각이 ISO 8601 + 오프셋 형식인가? (「확정 상태 기록」 참고)
- [ ] **수정일**: `canvas-updated-at` 이 있는가(확정 여부와 무관하게 **모든 캔버스 필수**)? 이번에 캔버스를 고쳤는데 값이 옛날 그대로 남아 있지 않은가? ISO 8601 + 오프셋이고 시:분까지 있는가(날짜만 적혀 있지 않은가)? 확정 표기를 넣은 것만으로 수정일을 올리지는 않았는가? (「수정하면 수정일을 남긴다」 참고)
- [ ] **파일 위치**: `one-canvas/<기획-건>/` 하위에 있는가? 기획 건 폴더가 kebab-case인가? 실무 산출물인데 `sample/` 하위에 만들어져 있지 않은가? 같은 기획 건의 캔버스가 여러 폴더로 흩어져 있지 않은가?
- [ ] **파일명**: A는 `canvas-{platform}-{화면명}.html`, B는 `canvas-{platform}-{에픽명}-noscreen.html` 형식을 따르는가?

## 통합캔버스 리뷰 프롬프트

```
아래 통합캔버스 html을 one-canvas/one-canvas-rule.md 기준으로 리뷰해줘.

[리뷰 대상]
<html 파일 경로 또는 내용을 붙여넣는다>

[리뷰 방식]
- 위 "통합캔버스 리뷰 체크리스트" 항목을 하나씩 대조해줘.
- 「수정일」·「확정 표기」 항목을 특히 빼먹지 마. 캔버스를 고쳐놓고 canvas-updated-at 을
  안 올린 경우가 가장 흔한 누락이고, 값이 그대로라 눈으로는 티가 안 난다.
- 통과한 항목은 나열하지 말고, 규칙과 다르거나 누락된 부분만 짚어줘.
- 어느 섹션의 어느 규칙을 위반했는지 근거를 함께 제시해줘.
- 수정이 필요하면 구체적으로 어떻게 고치면 되는지 제안해줘.
```

## 에픽 예시

**글로벌 배송 서비스 구축**

- **목적**: 해외 거주 고객의 구매 전환율을 높이기 위해 해외 배송 옵션을 추가한다.
- **주요 범위 (In-Scope)**:
  - 결제 페이지 내 해외 주소 입력 폼 추가
  - DHL, FedEx API 연동 및 실시간 배송비 계산
- **제외 범위 (Out-of-Scope)**:
  - 반품/교환 프로세스 (다음 에픽으로 이관)
  - 관세 자동 계산 기능 (1단계에서는 수동 안내로 대체)
- **완료 기준**: 사용자가 해외 주소를 입력하고, 배송비를 확인한 뒤, 해외 카드로 결제에 성공해야 한다.

## 유저스토리 예시 (GWT)

- **story-password-reset-request (비밀번호를 잊은 사용자가 재설정 링크를 요청한다)**
  - Given 가입된 이메일을 가진 사용자가 재설정 요청 화면에 있고, When 등록된 이메일을 입력해 재설정 링크를 요청하면, Then 해당 이메일로 재설정 링크가 발송된다.
  - Given 가입되지 않은 이메일이 입력되었고, When 재설정 링크를 요청하면, Then 계정 존재 여부를 노출하지 않는 동일한 안내 문구를 보여준다.
- **story-settlement-summary-view (파트너가 이번 달 정산 현황을 요약해서 확인한다)**
  - Given 이번 달 정산 데이터가 있는 파트너가 정산 화면에 접속했고, When 요약 영역을 확인하면, Then 이번 달 정산 총액·상태별 건수가 한눈에 요약되어 표시된다.

두 예시 모두 스토리 이름에 "누가·무엇을·왜"가 드러나고, 본문은 GWT 시나리오로 동작을 서술한다 — 정상/예외 분기는 시나리오를 나눈다. 예외까지 망라한 상세 수락 기준·성공/실패 테스트는 2단계(agile-issue)에서 다룬다.

## 플로우 예시

`epic-partner-settlement-detail (파트너 정산 상세 조회)` 캔버스의 플로우다. 캔버스에는 아래 소스를 `<pre class="mermaid">` 안에 그대로 넣는다.

```
flowchart TD
    A[화면 1 · settlement-list<br/>정산 내역 목록] --> B{행 클릭}
    B --> C[화면 2 · settlement-detail<br/>정산 상세 모달 오픈]
    C --> D[파트너명 + 산출 근거 4항목 표시]
    D --> E{닫기}
    E -->|닫기 버튼 / ✕ / 배경 / ESC| F[모달 닫힘<br/>목록 조회 상태 보존]

    D --> G{정산내역 다운로드}
    G --> H[다운로드 시작 + 안내 노출]

    D -.조회 실패.-> I[소유권 거부 / 없는 ID / API 실패<br/>→ 에러 안내, 닫기 경로 유지]
```

**근거 대조** — 모든 노드가 **바로 위 유저스토리·에픽**에서 왔다는 것을 확인할 수 있어야 한다. 플로우가 유저스토리 다음에 오는 이유가 이 대조를 위해서다.

| 노드 | 근거 |
|---|---|
| A → C (행 클릭 → 상세) | 유저스토리 GWT `Given 목록이 표시된 상태에서, When 정산 건을 클릭하면, Then 상세를 보여준다` |
| D → H (다운로드) | 유저스토리 GWT `When 정산내역 다운로드를 요청하면, Then 다운로드가 시작되고 안내를 보여준다` |
| E (4가지 닫기 경로) | 화면 2 UI 디스크립션의 인터랙션 정의 |
| I (조회 실패 분기) | 화면설명의 예외·경계 처리 |
| A (목록 화면) | **다른 에픽**(`canvas-partner-settlement-list.html`)이 소유 → 진입 노드 1개로만 표시하고 내부를 펼치지 않았다 |

근거 칸을 채울 수 없는 노드가 나오면 그것이 **지어낸 흐름**이다. 그리지 말고 질문한다.
