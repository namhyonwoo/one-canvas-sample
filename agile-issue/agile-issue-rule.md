# 애자일 이슈 (agile-issue)
# 신규/수정 개발건 애자일 이슈 작성 규칙

> 이 문서는 **AI가 신규/수정 개발건의 요구사항을 명세하고 지라(Jira) 태스크 단위로 분해할 때 그대로 따르는 실행 지시문**이다.
> 신규개발은 항상 기획/디자인 통합문서(one-canvas)를 참조하여 생성해야한다.
> 수정작업은 요구사항 명세서+코드베이스를 참고하여 생성할 수 있다.

---

## 개발 착수 규칙 (디자인 시스템 재사용 원칙)

> 애자일 이슈가 작성된 뒤 실제 구현(프론트/백엔드/앱)에 착수할 때 따르는 규칙이다. **문서 하나만 읽고 착수하면 반드시 무엇인가를 지어내게 된다** — 아래 단일 출처 표가 그 이유이고, 필수 참조 절차가 그 예방책이다.

### 문서별 단일 출처 (필수 — 착수 전에 읽는다)

같은 화면에 대한 정보가 여러 문서에 나뉘어 있고, **각 문서가 소유한 것이 서로 다르다.** 어느 하나를 안 읽으면 그 문서가 소유한 정보를 추측으로 메우게 된다.

| 문서 | 무엇의 단일 출처인가 | 안 읽으면 무엇을 지어내게 되나 |
|---|---|---|
| 스토리 `index.md` | 동작 · 기능 정책 · AC · 태스크 · 테스트 · 예외 · 권한 | 예외 처리, 경계값, 권한 검증, 상태 보존 규칙 |
| **캔버스 화면 앵커** (A유형) | **배치 · 비율 · 정렬 · 여백 · 화면 카피 · 컴포넌트 태깅(story id)** | **레이아웃 전체, 어떤 variant/story를 쓸지** |
| 에픽 `index.md` 「흐름도」 | 처리 순서 · 분기 조건 (캔버스 「플로우」 계승 — A·B 공통) | 단계 순서, 조건 분기 |
| 에픽 `index.md` 「참조 자료」 | 화면 앵커 · Figma 링크 · 디자인 시스템 참조 디렉터리 | 어느 캔버스의 어느 화면인지 |
| `design-system` | 컴포넌트 실물(props·variant) | 컴포넌트 인터페이스 |
| 도메인 `index.md` | 도메인 전반의 불변 규칙 | 여러 에픽에 공통 적용되는 정책 |

**스토리 md만으로 착수하면 기능은 맞고 형태는 틀린다.** 스토리는 항목 순서·라벨 문구·컴포넌트 디렉터리까지 담지만, 배치와 story id는 담지 않는다 — 그것은 캔버스가 소유한다(「참조 자료 작성 규칙」의 "화면 구성의 단일 출처는 캔버스 태깅" 참고).

**화면 없는 스토리(B유형)는 캔버스가 배치 대신 흐름을 소유한다.** 캔버스에 화면이 없으므로 3~4번 절차가 해당 없고, 대신 에픽 「흐름도」(캔버스 「플로우」 계승)가 처리 순서·분기의 단일 출처다.

### 필수 참조 절차 (프론트엔드)

화면이 있는 스토리를 구현할 때는 아래 순서를 건너뛰지 않는다.

1. **스토리 `index.md`를 읽는다** — 기능 정책·AC·태스크·열린 질문.
2. **에픽 `index.md` 「참조 자료」에서 앵커를 찾는다** — 스토리 헤더 `대상 화면`의 화면 번호로 표에서 찾는다.
3. **캔버스 화면을 실제로 연다** — `<캔버스 파일>#<앵커>`. 배치·번호 영역·화면 카피를 눈으로 확인하고, 해당 영역의 `<!-- component: X | story: … -->` 태깅에서 story id와 컴포넌트 파일 경로를 가져온다.
4. **story id로 스토리북에서 실물을 확인한다** — `http://localhost:{포트}/?path=/story/{story id}` (어드민·파트너 6008, 앱 6007).

**3번을 건너뛴 구현은 배치를 지어낸 것이다.** 그렇게 만든 레이아웃은 나중에 캔버스와 대조될 때 무엇이 근거 있는 결정이고 무엇이 임의 결정인지 구별되지 않는다.

### 지어내지 않는다 (금지)

「형식을 지킬 수 없으면 질문한다」의 구현 단계 확장이다. 아래는 추측으로 채우지 말고 **질문한다.**

- **캔버스에 없는 레이아웃·배치** — 화면에 없는 영역을 새로 배치하거나, 정렬·여백을 임의로 정하지 않는다. 캔버스가 화면 구성의 단일 출처다.
- **태깅이 누락된 요소** — 어떤 컴포넌트를 쓸지 임의로 정하지 않는다.
- **"디자인 시스템 미보유" 항목** — 컴포넌트를 새로 만들지도, 대체 UI를 임의로 만들지도 않는다. 이 작업 범위가 아니다(「태스크 범위에서 제외되는 작업 — 디자인 시스템」 참고). 미보유 항목은 **화면별 UI 디스크립션(우측 패널 `.screen-desc`) 하단**에 명시되어 있다.
  - 단, **화면 영역까지 보류하는 것은 `신규 필요` 한 가지뿐이다.** 나머지 3분류(`variant 값 추가 필요` / `참조 전용(page-local)` / `공용화 필요`)는 컴포넌트가 이미 존재하므로 그 화면 영역은 정상적으로 구현한다.
- **이슈·캔버스에 근거가 없는 동작·정책** — 그럴듯하게 채우는 것이 가장 위험하다.
- **스토리의 「열린 질문」에 걸린 항목** — 확정되기 전에는 구현하지 않는다.

### 착수 프롬프트 (화면 있는 스토리 — 프론트엔드)

```
아래 스토리를 구현해줘. 문서를 하나만 읽고 착수하지 마.

[읽을 것 — 순서대로]
1. <도메인>/epic-<에픽명>/story-<스토리명>/index.md
   → 기능 정책 · 수락 기준(AC) · 태스크 · 열린 질문
2. <도메인>/epic-<에픽명>/index.md 「참조 자료」
   → 1번의 `대상 화면` 번호로 화면 앵커를 찾아라
3. 그 앵커로 캔버스 화면을 실제로 열어라 (<캔버스 파일>#<앵커>)
   → 배치 · 번호 영역 · 화면 카피를 확인하고,
     `<!-- component: X | story: … -->` 태깅에서 story id와 컴포넌트 경로를 가져와라
   → 태스크의 [ui: 화면N ○ 카테고리/컴포넌트] 태그가 어느 영역인지 알려주지만,
     배치·카피·story id는 캔버스만 갖고 있다. 태그만 보고 착수하지 마.
4. design-system/<admin-partner | app> 에서 그 컴포넌트를 import 해라. 새로 만들지 마.

화면 없는 스토리(B유형)나 백엔드 전용 태스크는 2~4를 건너뛴다.
스토리 index.md + 에픽 「흐름도」 + 도메인 정책만으로 착수한다.

[문서별 소유 범위 — 섞지 마]
- 동작 · AC · 예외 · 권한  → 스토리 index.md
- 배치 · 정렬 · 화면 카피 · story id → 캔버스 화면
- 목록과 태깅이 어긋나면 캔버스 태깅을 따른다

[질문해야 하는 것 — 추측으로 채우지 마]
- 캔버스에 없는 레이아웃·배치가 필요해졌다
- 태깅이 누락된 요소가 있다
- "디자인 시스템 미보유"의 `신규 필요` 항목이다 (화면 영역째 보류 — 건너뛰고 질문)
  나머지 3분류는 컴포넌트가 이미 있으니 화면은 정상 구현하고,
  디자인 시스템 쪽 작업(컴포넌트 추가·variant 추가·공용화)만 하지 마
- 이슈·캔버스에 근거가 없는 동작·정책이 필요해졌다
- 스토리 「열린 질문」에 걸린 항목이다 (확정 전 구현 금지)

3번을 건너뛰면 배치를 지어낸 것이다. 캔버스를 열 수 없으면 멈추고 물어봐.
```

## 애자일 이슈 (agile-issue)란

- **애자일 이슈 (agile-issue)** 는 신규 개발건의 **정책 + 태스크가 포함된 명세 문서를 계층 구조로 구조화한 것**이다.
- 산출물은 모두 **Markdown(`.md`)** 형식으로 작성한다.

### 계층화하는 이유
AI가 자료를 효율적으로 탐색하고, **불필요한 컨텍스트 오염 없이 최소 토큰으로 필요한 계층만 읽도록** 하기 위함이다. 따라서 각 계층은 자기 책임 범위만 기술하고, 하위 상세는 하위 계층으로 내린다.

## 작성 기반
항상 기획/디자인문서 html(one-canvas)을 기반으로 하여 애자일 이슈를 생성한다. 

### 기획/디자인 문서
프로젝트 내 `one-canvas` 디렉터리.  

### 디자인 시스템 
프로젝트 내 `design-system` 디렉터리. 프론트엔드 작업시 항상 참조해야한다.
- 어드민/파트너: admin-partner 디렉터리
- 앱 : app디렉터리

## 용어 정의

### 캔버스 경로 (라우팅)

에픽 `index.md`의 `캔버스:` 줄에 적힌 one-canvas 파일 경로. **이 에픽이 어느 캔버스에서 파생되었는가**만 답한다.

- **에픽에만 둔다.** 에픽은 캔버스와 1:1로 대응하는 유일한 계층이다 — 도메인은 서로 다른 캔버스에서 파생된 에픽을 여러 개 아우르고, 스토리는 상위 에픽과 항상 같은 캔버스를 쓴다.
- 도메인·스토리는 이 경로를 반복 기재하지 않는다. 두 곳에 적으면 캔버스 파일명이 바뀔 때 한쪽만 갱신되어 엉뚱한 파일을 보게 된다.
- **one-canvas 클론 루트 기준 상대 경로로 적는다.** 절대 경로를 적지 않는다 — one-canvas는 작업 코드베이스와 별개 저장소이고 클론 위치는 환경마다 다르다. 클론 경로는 실행 시 프롬프트가 주입하며(「반입룰」 참고), 이 줄과 합쳐 실제 파일을 찾는다.

### 최신 대조 (reconcile)

반영 상태를 별도 값으로 기록하지 않고, **캔버스 최신본과 이슈의 현재 내용을 직접 대조해** 어긋난 곳을 찾는 방식. 이 문서의 동기화는 전부 이 방식이다.

**캔버스 HEAD가 항상 정본이다.** 이슈가 캔버스와 다르면 이슈를 고친다. "어디까지 반영했는지"를 기록할 필요가 없으므로 부분 반영을 표현할 장치도 필요 없다 — 이번에 손대지 않은 스토리는 다음 대조에서 또 어긋난 채로 잡힌다.

**이슈 문서에 캔버스 커밋 SHA를 적지 않는다.** one-canvas와 작업 코드베이스는 **별개 저장소이므로**, 이슈 쪽에 적힌 캔버스 커밋은 다른 저장소의 식별자여서 이슈가 사는 저장소에서 검증되지 않는다. 낡거나 틀려도 조용히 통과한다. 대조는 시작점을 묻지 않으므로 이 값이 애초에 필요 없다.

**대조 대상은 캔버스에서 파생된 내용뿐이다.** 이슈는 캔버스의 복사가 아니라 상위집합이다 — AC는 예외를 보강하고, 태스크는 개발자가, 테스트는 QA가 얹는다. 얹은 내용은 캔버스에 없는 것이 정상이므로 대조에서 제외하며, 무엇이 얹은 것인지 문서에 표시해 구별한다.

| 대조 대상 (캔버스 파생) | 대조 제외 (이슈가 얹은 것) |
|---|---|
| 에픽 계승 5항목 · 참조 자료 · 하위 스토리 목록 | 에픽 정책 |
| User Story · 기능 정책 · 표시 없는 AC | `(보강)` 표시된 AC · 태스크 · 테스트 |

- 표시 규칙은 「스토리 작성 규칙」의 AC 항목과 「에픽 작성 규칙」 참고.
- **이 구별이 "삭제 판정"의 근거다.** 표시 없는 AC인데 캔버스에 대응 GWT가 없으면 그 정책은 캔버스에서 삭제된 것이고, 그 AC를 참조한 태스크·테스트가 폐기 후보가 된다(「최신화 규칙」 참고).

### 반입 (bring-in)

**one-canvas 기획 변경을 작업 코드베이스 쪽으로 끌어오는 방향**을 가리킨다. 실제 서비스 코드를 만드는 저장소(groupbuy-next 등)에서 작업하다가, 그 사이 바뀐 기획을 애자일 이슈와 코드에 반영하는 것이다.

절차·제안 형식·실행 프롬프트는 이 문서 하단 **「반입룰 (bring-in)」** 에 있다 — 「기획(통합캔버스) 최신화 시 기존 이슈 반영 규칙」 바로 다음 섹션이다.

**방향을 반드시 구분한다** — 이 저장소에는 반대 방향 동기화도 있다. `design-system/`은 서비스 코드베이스의 컴포넌트를 **미러링해 들여오는**(코드 → one-canvas) 쪽이고, 반입은 **기획을 내보내는**(one-canvas → 작업) 쪽이다. 둘은 대상도 방향도 다르다.

## 디렉토리 구조와 작성 원칙

계층은 **도메인 → 에픽 → 스토리** 순이며, 각 계층은 디렉토리로 표현한다. 태스크는 별도 계층(디렉토리)이 아니라 스토리 `index.md` 내부의 섹션이다.

```
<도메인>/                     ← 디렉토리
  index.md                    ← 도메인 명세
  epic-<에픽명>/              ← 에픽 디렉토리
    index.md                  ← 에픽 명세
    story-<스토리명>/         ← 스토리 디렉토리
      index.md                ← 스토리 명세 (태스크·테스트 포함, 별도 파일 없음)
```

### 규칙:
- **모든 계층 디렉토리에 `index.md`가 존재**하며, 해당 계층의 명세서 역할을 한다.
- 스토리의 `index.md` 안에 스토리 설명·태스크·테스트를 **모두 인라인으로** 기술한다. 태스크를 별도 파일로 분리하지 않는다.

### 명명 규칙 (반드시 준수)
- 디렉토리·파일명은 **kebab-case** (소문자 + 하이픈).
- 계층 디렉터리는 접두사를 붙인다: 에픽은 `epic-`, 스토리는 `story-`. (도메인은 접두사 없이 도메인명 그대로)
- 이름은 영문으로, 의미를 드러내는 동사/명사 조합. 예: `epic-member-join`, `story-member-create`.
- `index.md`의 제목(H1)에는 **영문명 뒤에 한글명을 괄호로 병기**한다. 예: `# 에픽: member-join (회원가입)`.

### 문서 메타데이터 (frontmatter)
모든 `index.md` 상단에 YAML frontmatter를 둔다.
- `updated`: 마지막 내용 수정일. **모든 계층 필수.** 내용을 수정할 때마다 갱신한다.
- `status`: 진행 상태. **스토리 필수**, 도메인·에픽은 생략한다.
- `draft`(명세 작성 중) → `ready`(명세 확정, 개발 착수 가능) → `in-progress`(개발 중) → `done`(개발 완료)
- `changed-after-done`: **`done` 이후 기획이 변경**되어 재작업이 필요한 상태. 재작업 완료 시 다시 `done`으로 되돌린다.

### 형식을 지킬 수 없으면 질문한다 (필수)

**판정 기준·금지 행동·질문 방식의 원칙은 `one-canvas/one-canvas-rule.md` 「형식을 지킬 수 없으면 질문한다」에 있다.** 여기서는 agile-issue 계층에서 실제로 막히는 지점만 덧붙인다.

핵심만 다시 적으면 — **캔버스에 근거가 없어 지어내야 하는 항목이 나오면 확정하지 말고 질문한다.** 애자일 이슈는 캔버스에서 파생되므로, 여기서 지어낸 한 줄은 곧 AC·태스크·테스트로 증폭된다.

**질문해야 하는 지점 (agile-issue 고유)**

- **AC에 없는 정책이 필요하다** — 테스트나 태스크를 쓰다 보니 캔버스·AC 어디에도 없는 규칙이 필요해졌다. 테스트가 정책을 새로 만들면 안 된다(「스토리 작성 규칙」 참고).
- **정책의 소유 계층을 못 정한다** — 도메인 / 에픽 / 스토리 중 어디가 소유해야 할지 판단이 안 선다(「정책 단일 출처 원칙」 참고).
- **캔버스 태깅이 누락된 화면 요소**가 있어 어떤 컴포넌트를 쓸지 정할 수 없다 — 프론트·앱 태스크의 UI 태그를 채울 수 없다는 뜻이므로 임의로 정하지 않는다.
- **AC가 캔버스 GWT 계승분인지 이슈 보강분인지 판단이 안 선다** — `(보강)` 표시를 잘못 달면 대조가 그 AC를 삭제로 오판하거나 반대로 영구히 건드리지 않는다(「AC 출처 표시와 번호 규칙」 참고).
- **에픽 계승 5항목(4항목 + 플로우)을 계승할 수 없다** — 캔버스 원문에 해당 내용이 없다. 지어내지 말고 캔버스를 먼저 고친다. 특히 캔버스에 「플로우」가 없으면 여기서 흐름도를 새로 그리지 말고 캔버스에 먼저 추가한다.
- **디자인 시스템 미보유 항목의 분류**(`신규 필요` / `variant 값 추가 필요` / `참조 전용(page-local)` / `공용화 필요`)가 캔버스에 없어 화면 영역을 보류할지 판단이 안 선다(「태스크 범위에서 제외되는 작업 — 디자인 시스템」 참고).

**기록 방법**: 답이 오지 않은 항목은 스토리 `index.md`의 `### 열린 질문 (기획 확인 필요)` 섹션에 남긴다. 그 항목에 걸린 AC·태스크·테스트는 **확정될 때까지 만들지 않고**, 확인이 끝나면 열린 질문에서 지우고 본문에 반영한다.

### 정책 단일 출처 원칙 (Single Source of Truth)
같은 정책이 여러 계층에 중복 기술되면, 기획 수정 시 한쪽만 갱신되어 계층 간 모순(drift)이 발생한다. 이를 막기 위해:

- 하나의 정책 상세는 **그 정책을 소유한 계층의 `index.md` 한 곳에만** 기술한다.
- 소유 계층 판정 기준:
  - 도메인 전반의 불변 규칙 → **도메인**
  - 여러 스토리에 걸치는 정책 → **에픽**
  - 단일 스토리에만 해당하는 정책 → **스토리**
- 다른 계층에서 언급이 필요하면 **한 줄 요약 + 참조**만 남긴다. 예: `가입 입력값 정책 상세: story-member-create 참조`

### 도메인 작성 규칙
도메인 `index.md`는 one-canvas 통합캔버스의 **도메인** 소제목을 계승한다.

- 도메인명은 one-canvas와 동일하게 **접두사 없이 영문 kebab-case + 한글명 병기**로 적는다. 예: `settlement (정산)`.
- **도메인에는 `캔버스:` 줄을 두지 않는다.** 하나의 도메인 아래에는 서로 다른 캔버스에서 파생된 에픽이 여러 개 붙을 수 있어, 캔버스 파일 하나로 도메인을 대표할 수 없기 때문이다(「용어 정의」 참고). 모든 캔버스는 최소 하나의 에픽이 가리키므로 캔버스 쪽에 사각지대는 생기지 않는다.
- 대신 **도메인 정책의 최신성은 하위 계층을 대조할 때 함께 판정한다** — 「최신화 규칙」의 도메인 항목 참고. 도메인은 대응할 캔버스가 없어 단독으로 대조되지 않으므로, 이 판정을 빼먹으면 도메인 정책만 옛 기획에 머문다.
- **도메인 전반의 불변 규칙**(여러 에픽·스토리에 공통 적용되는 정책)만 이 계층에 소유한다. 특정 에픽/스토리에만 해당하는 정책은 내려보낸다(정책 단일 출처 원칙 참고).
- **참고 자료(Figma·엑셀 등)는 도메인이 아니라 에픽이 소유한다.** one-canvas에서는 참고 자료가 도메인 바로 다음에 오지만(one-canvas-rule.md 참고), agile-issue에서는 하나의 도메인 아래에 여러 캔버스에서 파생된 에픽이 붙을 수 있으므로 캔버스 단위(=에픽)로 내려보낸다 — 에픽 작성 규칙의 「참조 자료」 참고.
- **하위 에픽**(epic-* 목록)을 나열한다.

### 에픽 작성 규칙
에픽 `index.md`는 one-canvas 통합캔버스의 **에픽** 소제목(목적 / 주요 범위(In-Scope) / 제외 범위(Out-of-Scope) / 완료 기준)과 **플로우** 소제목을 그대로 계승해서 작성한다.

- 계승 5항목(에픽 4항목 + 플로우) 모두 필수. one-canvas 원문을 그대로 옮기고 새로 지어내지 않는다.
- **흐름도는 캔버스 「플로우」의 mermaid 소스를 그대로 옮긴다.** 새로 그리지 않는다 — 캔버스가 흐름의 단일 출처다(one-canvas-rule.md 「플로우 명세 수준」 참고). 캔버스 소스가 `<pre class="mermaid">` 평문인 이유가 이 복사를 위해서다.
- 아래 한 줄을 남긴다 (의미는 「용어 정의 — 캔버스 경로」 참고).
  ```
  > 캔버스: <one-canvas 클론 루트 기준 상대 경로>
  ```
- **`캔버스:` 줄은 에픽에만 둔다.** 도메인은 여러 캔버스를 아우르고 스토리는 상위 에픽과 같은 캔버스를 쓰므로, 에픽이 캔버스와 1:1로 대응하는 유일한 계층이기 때문이다.
- **캔버스 커밋 SHA를 적는 줄은 두지 않는다.** 반영 상태를 기록하지 않고 캔버스 최신본과 직접 대조한다(「용어 정의 — 최신 대조」 참고).
- 위 계승 항목 외에 agile-issue 단계에서만 추가하는 항목: **참조 자료**(화면 목록 + 참고 자료 + 디자인 시스템), **에픽 정책**(여러 스토리에 걸치는 정책 — 정책 단일 출처 원칙 참고, 없으면 생략), **하위 스토리**(story-* 목록). (**흐름도**는 여기 속하지 않는다 — 캔버스 「플로우」를 계승하는 항목이다.)
- **「에픽 정책」은 대조 대상이 아니다.** 계승 5항목·참조 자료·하위 스토리 목록은 캔버스에서 파생되므로 캔버스와 다르면 캔버스를 따르지만, 에픽 정책은 여러 스토리에 걸친다는 이유로 끌어올린 것이어서 캔버스에 대응 문장이 없을 수 있다. **캔버스에 없다는 이유로 지우지 않는다.**

#### 참조 자료 작성 규칙 (에픽 소유)

`캔버스:` 줄은 **에픽↔캔버스 라우팅**이지 화면 구현용 참조가 아니다. 프론트엔드가 화면을 만들 때 어느 캔버스의 어느 화면을 열어야 하는지 매번 찾아 헤매지 않도록, 에픽 `index.md`에 **참조 자료** 섹션을 따로 둔다.

- **화면 목록**: 캔버스가 A유형(화면 있음)이면 화면마다 한 줄씩 `화면 번호 / 화면명(영문 + 한글) / 앵커 / 대응 스토리`를 표로 적는다.
  - 앵커는 캔버스 html의 `<section class="screen-block" id="...">` 값을 그대로 옮긴다. 브라우저에서 `<캔버스 파일>#<앵커>`로 해당 화면이 바로 열린다.
  - B유형(화면 없음)이면 화면 목록 표는 생략한다.
- **참고 자료**: one-canvas의 `참고 자료` 섹션(Figma 시안, 엑셀, 노션 등)을 `자료명 — 링크 — 한 줄 설명` 형식 그대로 계승한다. 캔버스에 해당 섹션이 없으면 생략한다.
- **캔버스 파일 경로는 `캔버스:` 한 줄에만 적는다.** 화면 목록에는 앵커만 적고 "앵커는 `캔버스:` 파일 기준"임을 밝힌다. 경로를 두 곳에 적으면 캔버스 파일명이 바뀔 때 한쪽만 갱신되어, 대조가 엉뚱한 파일을 보게 된다.
- **디자인 시스템**: 이 에픽의 화면이 참조할 `design-system` 하위 디렉터리를 한 줄로 밝힌다(어드민/파트너 → `admin-partner`, 앱 → `app`). 프론트엔드가 어느 디자인 시스템을 볼지 에픽만 읽고 알 수 있어야 한다.
  - 사용 컴포넌트 목록을 함께 적을 수 있으나, 어디까지나 **참조용 요약**이다. 화면 구성의 단일 출처는 캔버스의 `<!-- component: X -->` 태깅이며, 목록과 태깅이 어긋나면 태깅을 따른다.
- **참고 자료의 소유 계층은 에픽이다.** 하나의 도메인 아래에 서로 다른 캔버스에서 파생된 에픽이 여러 개 있을 수 있고, 참고 자료는 캔버스(=에픽)마다 다르기 때문이다. 도메인·스토리에서 언급이 필요하면 한 줄 요약 + 참조만 남긴다(정책 단일 출처 원칙).
- 캔버스에 없는 링크(화면별 Figma node URL 등)를 임의로 지어내지 않는다. 캔버스에 있는 링크만 그대로 옮긴다.

#### 캔버스 확정 표기 (최초 이슈 생성 시 · 필수)

에픽 `index.md`를 **처음 만들면**, 그 에픽의 `캔버스:` 줄이 가리키는 **캔버스 파일에 확정 표기를 기록한다.** 형식(meta 4종 + body 최상단 배지)은 one-canvas-rule.md 「확정 상태 기록」에 있고, 여기서 정하는 것은 **언제 기록하는가**다.

**왜 이슈 생성 시점인가**: 확정은 "이 캔버스의 기획을 모두 동의하고 애자일 이슈를 최초로 생성했다"는 뜻이다. 그 사건이 일어나는 곳이 정확히 여기다. 이 단계에서 기록하지 않으면 캔버스는 영원히 미확정으로 남고, 리뷰어는 이미 개발이 시작된 문서를 초안으로 착각한 채 코멘트를 단다.

- `canvas-confirmed-at` — **이슈를 생성한 시각** (ISO 8601 + 오프셋).
- `canvas-confirmed-issue` — 방금 만든 **에픽 디렉터리 경로**를 `캔버스:` 줄과 대칭이 되게 저장소 루트 기준으로 적는다. 예: `agile-issue/partner-review/epic-partner-business-info`.
- **이미 확정 meta가 있으면 덮어쓰지 않는다.** 한 캔버스에서 두 번째 에픽이 나오는 일은 원칙적으로 없지만(캔버스 1개 = 에픽 1개), 있더라도 **최초 값이 정본**이다. 이슈를 지웠다가 다시 만든 경우도 마찬가지다.
- 「최신 대조」로 캔버스를 고칠 때는 **`canvas-updated-at` 만 갱신**한다. 확정 시각은 건드리지 않는다. 이 값은 확정과 무관하게 모든 캔버스가 갖는 필수 값이며, 규칙은 one-canvas-rule.md 「수정하면 수정일을 남긴다」가 소유한다 — 캔버스를 고쳤으면 이슈 쪽 `updated:` 를 올리듯 캔버스 쪽 수정일도 올린다.
- **캔버스 파일에 접근할 수 없으면 확정 표기를 지어내지 말고 멈추고 알린다.** one-canvas와 작업 코드베이스는 별개 저장소일 수 있어(「용어 정의 — 최신 대조」), 캔버스가 없는 환경에서 이슈만 만들게 되는 경우가 있다. 그때는 **기록하지 못한 채 남기는 것이 맞고**, 캔버스가 있는 환경에서 나중에 채운다. 이슈 생성 시각을 짐작해 넣지 않는다(「형식을 지킬 수 없으면 질문한다」와 같은 원칙).

### 스토리 작성 규칙
- **스토리에는 `캔버스:` 줄도, 캔버스 커밋 SHA를 적는 줄도 두지 않는다.** 아래 한 줄만 남긴다(모든 스토리 공통 — 화면 없는 B유형도 포함).
  ```
  > 기획 출처: epic-<에픽명> 참조
  ```
  - **경로를 두지 않는 이유**: 스토리는 상위 에픽과 항상 같은 캔버스에서 파생되므로 경로가 중복되고, 캔버스 파일명이 바뀌면 여러 스토리 중 일부만 갱신되어 어긋난다.
  - **SHA를 두지 않는 이유**: 반영 상태를 기록하지 않고 캔버스 최신본과 직접 대조한다(「용어 정의 — 최신 대조」 참고). 이번에 손대지 않은 스토리는 다음 대조에서 또 어긋난 채로 잡히므로, 어느 스토리가 남았는지 기록해 둘 필요가 없다.
- `changed-after-done`은 **"이미 만든 코드에 재작업이 필요하다"는 개발 신호**로만 쓴다. `status`는 개발 진행 상태만 담고, 캔버스와 맞는지는 대조가 답한다.
- 화면이 있는 스토리는 출처 아래에 아래 2줄을 남겨 어느 화면의 어느 영역을 구현하는지 밝힌다. **캔버스 파일 경로·앵커·링크는 반복하지 않는다**(정책 단일 출처 원칙).
  ```
  > 대상 화면: <화면 번호> `<화면명>` — 번호 영역 <①②③…>
  > **구현 전 필수**: 위 화면을 캔버스에서 열어 배치·컴포넌트 태깅을 확인한다.
  > 앵커·Figma 시안은 `epic-<에픽명>/index.md` 「참조 자료」에 있다 — 이 스토리는 배치·story id를 소유하지 않는다.
  ```
  화면이 없는 스토리(B유형)는 이 3줄을 생략한다.
- **두 번째·세 번째 줄은 "참고"가 아니라 "필수"로 적는다.** 이 스토리에는 배치·정렬·여백·story id가 없고 그것은 캔버스가 소유하므로, 캔버스를 열지 않은 구현은 배치를 지어낸 것이다(「개발 착수 규칙」의 단일 출처 표 참고). "참조 자료 참고"처럼 선택으로 읽히게 적으면 스토리만 읽고 착수하는 것을 막지 못한다.
- `## User Story`는 one-canvas 유저스토리의 **스토리 이름(누가/무엇을/왜)**을 한 줄 요약으로 계승한다. (화면 없는 유저스토리는 사용자 대신 시스템/배치가 주체다 — one-canvas B유형 참고)
- **수락 기준(AC)은 Given-When-Then(GWT) 시나리오로 작성한다.** one-canvas 유저스토리의 GWT를 계승하고, 예외 케이스를 보강해 상세화한다(one-canvas-rule.md 유저스토리 명세 수준 참고).
  - 형식: `Given <사전 조건>, When <행동>, Then <기대 결과>`
  - 하나의 AC는 하나의 GWT 시나리오 단위로 쪼갠다. 조건 분기(정상/예외 등)가 있으면 시나리오를 분리한다.

#### AC 출처 표시와 번호 규칙 (대조의 근거 — 반드시 지킨다)

AC는 캔버스 대조에서 **삭제 판정이 일어나는 유일한 지점**이고, 태스크·테스트가 AC 번호로 그 판정을 물려받는다. 아래 두 규칙이 깨지면 대조 전체가 무의미해진다.

**1. 이슈에서 보강한 AC에는 `(보강)`을 붙인다.** 표시가 없는 AC는 캔버스 GWT 계승분이라는 뜻이다.

```
- [ ] **AC10** Given 선택한 조합에 해당하는 건이 없고, When 조회하면, Then 결과 없음 안내가 표시된다.
- [ ] **AC11** (보강) Given 허용되지 않은 상태 값이 전달되었고, When 조회를 요청하면, Then 검증 에러로 처리된다.
```

- 대조 시 **표시 없는 AC인데 캔버스에 대응 GWT가 없으면 그 정책은 캔버스에서 삭제된 것**이다. `(보강)` AC는 캔버스에 없는 것이 정상이므로 대조에서 건드리지 않는다.
- 표시를 빼먹으면 보강 AC가 삭제된 것으로 오판되어, 그것을 참조한 태스크까지 폐기 후보로 끌려간다.
- **실제로는 `(보강)`이 다수인 것이 정상이다.** 캔버스 유저스토리는 대표 시나리오만 GWT로 두고(one-canvas-rule.md 「유저스토리 명세 수준」 참고) 예외·경계값·상태 보존은 이슈가 상세화하므로, 스토리 하나에서 계승분이 1~3개뿐인 것이 흔하다. 표시가 많다는 이유로 규칙을 뒤집지 않는다 — `(계승)`을 소수에만 다는 방식은 표기량은 줄지만, 표시를 빼먹은 계승 AC가 **영구히 대조되지 않는 조용한 실패**가 된다. 지금 방향은 빼먹으면 삭제 오판으로 시끄럽게 드러난다.
- **캔버스 GWT 1개가 계승 AC 여러 개로 갈라지는 것은 정상이다**(조건 분기마다 시나리오를 분리하므로). 따라서 대조는 1:1 매칭이 아니다 — 어느 GWT에서 갈라진 것인지 판단이 안 서면 지어내지 말고 질문한다(「형식을 지킬 수 없으면 질문한다」 참고).

**2. AC 번호는 한 번 부여하면 영구 불변이다. 재번호하지 않는다.**

- 삭제된 AC는 **번호를 비우지 않고 자리에 남겨** `~~AC7~~ [폐기됨,YYYY-MM-DD HH:mm]`으로 표시한다. 태스크 라인을 지우지 않는 것과 같은 원리다(「태스크 작성규칙」 참고).
- 새 AC는 항상 **마지막 번호 다음**을 쓴다. 폐기된 번호를 재사용하지 않는다.
- **재번호는 태스크·테스트의 AC 참조를 통째로 어긋나게 만들면서 아무 흔적도 남기지 않는다.** AC3을 지우고 뒤 번호를 당기면 `(AC4)`를 참조한 태스크가 조용히 다른 정책을 가리킨다.
- **테스트는 수락 기준(AC)을 모두 커버해야 한다.** 모든 GWT 시나리오마다 그것을 검증하는 성공 또는 실패 테스트가 최소 1개 존재해야 하며, AC에 없는 정책을 테스트가 임의로 만들어내지 않는다.


### 태스크 작성규칙 및 상태 마킹 (작업 진행 상태 + 타임스탬프)

스토리의 **모든 태스크는 라인 앞에 구현 상태 마커**를 붙인다. 상태는 4종이다.

| 상태 마커 | 의미 | 타임스탬프 |
|---|---|---|
| `[생성됨,YYYY-MM-DD HH:mm]` | 아직 구현되지 않음 — 태스크 생성 시 기본값 | 생성된 시각 |
| `[진행중,YYYY-MM-DD HH:mm]` | 작업 진행중 | 진행중으로 바뀐 시각 |
| `[완료,YYYY-MM-DD HH:mm]` | 구현 완료 | 구현을 마친 시점 |
| `[폐기됨,YYYY-MM-DD HH:mm]` | 착수 이후 그 태스크가 철회된 상태 — 더 이상 필요 없어졌거나 내용이 대체되었다 | 폐기된 시점 |

- **폐기됨**의 기준은 **완료 여부가 아니라 착수 여부**다. `[진행중]`이라 아직 반쯤 만들어진 태스크도 폐기 대상이며, 그 경우에도 라인을 지우지 않는다 — 이미 들인 작업이 있었다는 사실이 이력이다.
- 태스크 라인은 지우지 말고 마커만 `[폐기됨,...]`으로 바꿔 이력을 남긴다.
- 아직 **작업 전(생성됨 단계)**에 필요 없어진 태스크는 폐기됨으로 두지 않고 **태스크 라인 자체를 삭제**한다.
- 마커는 **태스크 단위** 진행 현황이고, 스토리 frontmatter `status`는 **스토리 단위** 상태다 — 별개로 관리하되, `[생성됨]`·`[진행중]` 태스크가 남아 있는데 status가 `done`이면 모순이므로 함께 점검한다.
- **백필**: 마커 없이 이미 구현돼 있는 태스크를 발견하면, 해당 구현 커밋의 타임스탬프(`git log`)로 소급해 기록한다.

#### 태스크 라인 형식 (AC 참조 · UI 태그)

태스크 라인은 아래 형식으로 적는다. **AC 참조는 모든 태스크 필수, UI 태그는 Frontend·App 태스크 필수**다.

```
- [ ] [<상태 마커>] <태스크 내용> (<AC 참조>) [ui: <화면 번호> <번호 영역> <카테고리/컴포넌트명>]
```

예시:
```markdown
### Backend
- [ ] [생성됨,2026-07-31 12:35] 목록 조회 API에 `statuses[]` 다중 상태 파라미터 지원 추가 (AC2, AC3)

### Frontend
- [ ] [생성됨,2026-07-31 12:35] 상태 필터 체크박스 3종 구현 — 초기값 `완료`만 체크 (AC1) [ui: 화면1 ① inputs/checkbox]
- [ ] [생성됨,2026-07-31 12:35] 상태 칩 × 클릭 시 해당 체크박스 해제 후 즉시 재조회 (AC6, AC7) [ui: 화면1 ② inputs/filterChip]
```

**AC 참조 (모든 태스크 필수)**

- 그 태스크가 어느 AC를 구현하는지 `(AC2, AC3)` 형태로 적는다. **AC가 폐기되면 그것을 참조한 태스크가 폐기 후보로 도출되는 경로가 이 참조뿐이다**(「최신화 규칙」 참고).
- 성능·인덱스·리팩터링처럼 AC에서 직접 나오지 않는 파생 태스크도 **근거가 되는 AC를 단다.** 예: 상태 조건 조회 성능 확보 → `(AC2, AC3)`.
- 어느 AC에도 걸 수 없는 태스크는 **AC가 빠진 것이거나 이 스토리의 태스크가 아니다.** 참조를 비우고 넘어가지 말고 질문한다 — 참조 없는 태스크는 대조에서 영구히 누락된다.

**UI 태그 (Frontend · App 태스크 필수)**

- 형식: `[ui: <화면 번호> <번호 영역> <카테고리/컴포넌트명>]`. 값은 모두 캔버스에서 가져온다 — 화면 번호·번호 영역은 스토리 헤더 `대상 화면`과 같은 표기, 컴포넌트 경로는 캔버스 `<!-- component: X -->` 태깅의 값을 그대로 옮긴다.
- **캔버스 화면이 바뀌었을 때 어느 프론트 태스크를 고쳐야 하는지 답하는 유일한 연결선이다.** 화면 번호만으로는 좁혀지지 않는다 — 화면 하나에 스토리가 여러 개 대응하고, 번호 영역 하나에 서로 다른 스토리의 요소가 섞이기도 한다.
- 한 태스크가 여러 컴포넌트를 다루면 쉼표로 나열한다: `[ui: 화면1 ② inputs/filterChip, inputs/checkbox]`.
- 화면 영역이 아닌 프론트 작업(전역 상태 배선, API 클라이언트 등)은 컴포넌트 자리를 비우고 영역까지만 적는다: `[ui: 화면1 ②]`.
- 태깅이 누락된 요소는 컴포넌트를 임의로 정하지 않는다. 「지어내지 않는다」에 따라 질문한다.
- 이 태그로 캔버스↔이슈를 양방향 추적한다.
  ```
  # 캔버스에서 컴포넌트 태깅이 바뀌었다 → 영향받는 태스크 찾기
  grep -rn "ui:.*inputs/checkbox" <도메인>/

  # 태스크의 컴포넌트 → 캔버스의 어느 화면·영역인지 찾기
  grep -rn "component:.*inputs/checkbox" <캔버스 파일>
  ```

#### 태스크 범위에서 제외되는 작업 — 디자인 시스템

**디자인 시스템(`design-system/`) 자체를 손대는 작업은 애자일 이슈의 태스크로 만들지 않는다.** 애자일 이슈의 태스크는 **서비스 구현**(backend / frontend / app)만 담는다.

- 태스크로 만들지 않는 것:
  - 디자인 시스템에 신규 컴포넌트 추가
  - 기존 컴포넌트에 variant 값 추가
  - page-local 컴포넌트를 공용으로 끌어올리는 공용화
  - 위 항목의 편입 여부를 논의·확인하는 작업
- 캔버스의 "디자인 시스템 미보유" 항목에서 **디자인 시스템 쪽 작업만** 빠진다. 애자일 이슈는 그 사실을 **에픽 `제외 범위`에 적어 범위 밖임을 밝히는 것까지만** 한다.

**중요 — 화면 영역까지 보류하는 것은 `신규 필요` 한 가지뿐이다.** 나머지 3분류는 컴포넌트가 이미 어딘가에 존재하므로, 그 화면 영역의 **수락 기준(AC)·태스크·테스트는 정상적으로 둔다.** 미보유로 표시됐다는 이유로 화면 구현 자체를 빼면, 프론트엔드가 실제로 만들어야 하는 영역이 명세에서 통째로 사라진다.

| 분류 | 디자인 시스템 쪽 작업 | 화면 영역 AC·태스크·테스트 |
|---|---|---|
| `신규 필요` | 제외 (신규 컴포넌트 추가) | **보류** — 어디에도 없어 편입 여부가 정해진 뒤 별도 스토리로 다룬다 |
| `variant 값 추가 필요` | 제외 (값 추가) | **둔다** — 컴포넌트는 이미 있다 |
| `참조 전용(page-local)` | 없음 (애초에 공용화 대상이 아니다) | **둔다** — 기존 page-local 컴포넌트를 그대로 쓴다 |
| `공용화 필요` | 제외 (공용으로 끌어올리기) | **둔다** — 현재 위치의 page-local 컴포넌트를 재사용하는 전제로 작성한다 |
- **애자일 이슈가 참조하는 디자인 시스템 정보는 유지한다** — 에픽 `참조 자료`의 「디자인 시스템」(참조 디렉터리 + 사용 컴포넌트 목록)은 프론트엔드가 **어떤 기존 컴포넌트를 import할지** 알기 위한 것이므로 태스크 범위 제외와 무관하다.

### 기획(통합캔버스) 최신화 시 기존 이슈 반영 규칙

통합캔버스(one-canvas) 기획이 수정되면, 그 기획에서 파생된 에픽/스토리/태스크를 최신 기획에 다시 맞춘다. **핵심 원칙: 이미 착수된 작업 이력은 덮어쓰지 않고 보존한다.**

**최신 대조 (3단계)** — 캔버스 최신본을 정본으로 두고 이슈와 직접 맞춰본다. 기준 커밋이나 diff 범위를 계산하지 않는다(「용어 정의 — 최신 대조」 참고).

> **대조는 에픽 1개 단위로 돌린다** — 에픽 `index.md` + 그 하위 스토리 전부. 캔버스는 에픽 `캔버스:` 값 하나로 찾는다.
>
> 어느 계층이 최신인지 미리 판정할 방법이 없으므로 **하위 스토리를 전부 훑는다.** 이미 맞는 스토리는 대조에서 "차이 없음"으로 끝나므로 손대지 않게 된다.

1. **읽는다** — 캔버스 파일 최신본, 그리고 대상 에픽 `index.md` + 하위 스토리 `index.md` 전부.
2. **대조한다** — 캔버스 파생 항목만 짝지어 본다. 이슈가 얹은 항목은 대조하지 않는다.

   | 이슈 쪽 | 캔버스 쪽 |
   |---|---|
   | 에픽 목적 / 주요 범위 / 제외 범위 / 완료 기준 | 「에픽」 소제목 |
   | 에픽 「흐름도」 | 「플로우」 mermaid 소스 |
   | 에픽 「참조 자료」 화면 목록 (번호·화면명·앵커) | `<section class="screen-block" id="...">` |
   | 스토리 「User Story」 | 유저스토리 이름 |
   | 스토리 「기능 정책」 | 화면 디스크립션 (`.screen-desc`) · 유저스토리 본문 |
   | 표시 없는 AC | 유저스토리 GWT |
   | 태스크 UI 태그 (`[ui: …]`) | 화면 번호 영역 · `<!-- component: X -->` 태깅 |

   대조 제외: 에픽 「에픽 정책」, `(보강)` AC, 태스크 내용, 테스트.
3. **어긋난 곳을 3종으로 분류한다** — 이 분류가 아래 처리 규칙의 입력이다.

   | 분류 | 판정 근거 | 처리 |
   |---|---|---|
   | **변경** | 양쪽에 다 있는데 내용이 다르다 | 이슈를 캔버스에 맞춘다 |
   | **신규** | 캔버스에 있는데 이슈에 없다 | AC·태스크·테스트를 추가한다 |
   | **삭제** | 표시 없는 AC(또는 계승 항목)인데 캔버스에 대응이 없다 | 그 AC를 폐기하고, 참조한 태스크를 폐기 후보로 도출한다 |

**삭제 판정과 연쇄 폐기**

삭제는 **표시 없는 AC와 에픽 계승 항목에서만** 판정한다. `(보강)` AC·태스크·테스트는 캔버스에 대응이 없는 것이 정상이므로 삭제로 보지 않는다.

AC가 삭제로 판정되면:
1. 그 AC를 `~~ACn~~ [폐기됨,YYYY-MM-DD HH:mm]`으로 바꾼다(번호는 자리에 남긴다 — 「AC 출처 표시와 번호 규칙」 참고).
2. `grep -n "ACn" <스토리 index.md>`로 그 AC를 참조한 태스크·테스트를 찾는다. **AC 정의 라인 자체는 결과에서 제외한다** — 방금 폐기 표시한 그 줄도 함께 걸린다.
3. 찾은 태스크를 아래 태스크 처리 규칙에 따라 다룬다.

- **참조 AC가 일부만 삭제된 태스크는 폐기 후보이지 폐기 확정이 아니다.** `(AC2, AC3)`에서 AC3만 삭제되면 그 태스크는 AC2 때문에 여전히 유효할 수 있다. 후보로 제시하고 **판정은 작업자가 한다** — 여기서는 「애매하면 폐기 쪽으로 기운다」를 적용하지 않는다(그 원칙은 정책이 통째로 대체된 경우를 위한 것이다).
- **AC 참조가 없는 태스크는 이 연쇄에 잡히지 않는다.** 태스크 라인 형식이 AC 참조를 필수로 둔 이유가 이것이고, 그럼에도 참조 없는 태스크를 발견하면 대조와 별개로 사람이 봐야 한다.

**화면 변경 → 프론트 태스크 도출**

화면이 바뀌면 AC 연쇄와 **별도로** 프론트 태스크를 도출한다. 배치·컴포넌트 교체·카피 변경은 AC 문장을 바꾸지 않고도 일어나므로, AC만 보면 이 변경이 통째로 누락된다.

라우팅은 태스크의 **UI 태그**로 한다 — 화면 번호·번호 영역·컴포넌트 경로가 들어 있어 캔버스 화면과 직접 짝지어진다(「태스크 라인 형식」 참고).

| 캔버스 화면의 변화 | 도출 |
|---|---|
| 번호 영역이 **추가**됐다 | 그 영역의 프론트 태스크를 **신규 추가**한다 (UI 태그를 새 영역·컴포넌트로 단다). 동작이 함께 정의됐으면 AC·테스트도 추가한다 |
| 번호 영역이 **삭제**됐다 | 그 영역의 UI 태그를 가진 태스크를 **폐기 후보**로 올린다 |
| **컴포넌트 태깅이 교체**됐다 (`inputs/checkbox` → `inputs/toggle`) | 착수 전이면 UI 태그와 내용을 **직접 수정**, 착수 이후면 **폐기 + 대체 태스크 신규 추가** |
| **배치·정렬·여백**이 바뀌었다 | 해당 UI 태그 태스크에 대해 착수 전이면 직접 수정, 착수 이후면 **레이아웃 수정 태스크를 신규 추가** (기존 태스크는 유효하므로 폐기하지 않는다) |
| **화면 카피**가 바뀌었다 | 위와 같이 처리한다. 카피는 캔버스가 단일 출처이므로 이슈에서 임의로 정하지 않는다 |
| 화면 자체가 **추가·삭제**됐다 | 에픽 「참조 자료」 화면 목록을 먼저 맞추고, 스토리 신설·폐기가 필요한지 판정한다 |

- **어느 스토리의 태스크인지는 UI 태그로 좁힌다.** 화면 번호만으로는 좁혀지지 않는다 — 화면 하나에 스토리가 여러 개 대응하고(에픽 화면 목록 참고) 번호 영역 하나에 서로 다른 스토리의 요소가 섞이기도 한다.
  ```
  # 바뀐 영역·컴포넌트로 영향받는 태스크 찾기
  grep -rn "ui:.*화면1 ②" <도메인>/
  grep -rn "ui:.*inputs/checkbox" <도메인>/
  ```
- **디자인 시스템 쪽 작업은 도출하지 않는다.** 캔버스에 "디자인 시스템 미보유"가 새로 붙어도 컴포넌트 신설·variant 추가·공용화는 태스크로 만들지 않는다(「태스크 범위에서 제외되는 작업」 참고). `신규 필요`는 화면 영역째 보류하고, 나머지 3분류는 화면 태스크를 정상 도출한다.

**대조가 잡지 못하는 것 (구조적 한계 — 알고 쓴다)**

캔버스 파일 밖에 실체가 있는 변경은 침묵한다. 「플로우 명세 수준」이 플로우를 이미지로 두지 말라고 한 것과 같은 이유다(one-canvas-rule.md 참고).

| 사각지대 | 왜 침묵하나 | 대응 |
|---|---|---|
| Figma 시안 내용 변경 | 캔버스엔 링크만 있어 node가 바뀌어도 캔버스 파일은 그대로다 | 디자이너·기획자가 캔버스를 함께 고쳐야만 잡힌다 |
| `design-system` 컴포넌트 변경 | 반대 방향 미러링이고, 캔버스 태깅이 그대로면 대조에 차이가 나타나지 않는다 | 컴포넌트 미러링 시 그 컴포넌트를 태깅한 캔버스·이슈를 따로 확인한다 (위 grep) |
| `(보강)` 표시가 잘못 붙은 AC | 대조가 그 AC를 건드리지 않거나(잘못 붙음) 삭제로 오판한다(빠뜨림) | 표시는 AC 작성 시점에 정확히 단다 |
| AC 참조·UI 태그가 없는 태스크 | 연쇄와 라우팅 양쪽에서 누락된다 | 태스크 라인 형식을 지키는 것이 전제다 |

**공통**
- 반영을 마치면 수정한 계층 `index.md`의 `updated`를 갱신한다(모든 계층).
- **이번에 손대지 않은 스토리는 아무 표시도 남기지 않는다.** 다음 대조에서 또 어긋난 채로 잡히므로 기록할 필요가 없다. 반대로, 대조에서 계속 같은 스토리가 뜨는 것은 실제로 미처리 작업이 남아 있다는 뜻이다.
- **도메인은 단독으로 대조되지 않는다.** 에픽·스토리를 대조할 때 그 변경이 도메인 정책(도메인 전반의 불변 규칙)에 영향을 주는지 **함께 판정**하고, 수정했으면 도메인 `index.md`의 `updated`를 갱신한다. 이 판정을 빼먹으면 도메인 정책만 옛 기획에 머무는 사각지대가 생긴다.
- 스토리가 이미 `done`인데 기획 변경으로 재작업이 필요하면 frontmatter `status`를 `changed-after-done`으로 바꾼다. 이것은 **"만든 코드에 재작업이 필요하다"는 개발 신호**다(「스토리 작성 규칙」 참고).

**에픽·스토리 (명세 내용 수정)**
- 목적·범위·GWT(수락 기준) 등 명세는 최신 기획에 맞게 **직접 수정**한다. 명세는 현재 기획의 단일 출처이므로 옛 내용을 남겨두지 않는다.

**태스크 (상태 마커에 따라 분기)** — 태스크는 작업 이력이므로 상태를 보고 처리를 나눈다. 착수 이후 태스크는 상태만으로 정하지 않고 **변경의 성격까지 함께 본다**:

| 태스크 현재 상태 | 변경의 성격 | 처리 방법 |
|---|---|---|
| `[생성됨]` (착수 전) | 무엇이든 | 태스크 내용을 **직접 수정**한다. 구현된 게 없어 덮어써도 잃을 이력이 없다. |
| `[진행중]` · `[완료]` · `[폐기됨]` (착수 이후) | 기존 태스크는 **그대로 유효**하고, 변경분이 별도 추가 작업이다 | 기존 태스크를 그대로 두고 변경분을 반영한 **신규 태스크를 추가**한다. 이미 진행/완료된 작업의 기록을 지우지 않기 위함이다. |
| `[진행중]` · `[완료]` (착수 이후) | 그 태스크가 **주장하는 정책 자체가 바뀌었다**(내용 대체) | 기존 태스크를 `[폐기됨,...]`으로 바꾸고(라인 삭제 X) **대체 태스크를 신규 추가**한다. |
| `[진행중]` · `[완료]` (착수 이후) | 그 태스크가 **더 이상 필요 없어졌다** | 기존 태스크를 `[폐기됨,...]`으로 바꾼다(라인 삭제 X). 대체 태스크는 없다. |

**왜 내용 대체를 폐기 처리하는가** — 착수 이후 태스크는 직접 수정이 금지되어 있다(작업 이력이므로). 그래서 정책이 바뀐 태스크를 그대로 둔 채 신규 태스크만 추가하면, **옛 정책을 주장하는 `[진행중]` 라인과 새 정책을 주장하는 `[생성됨]` 라인이 둘 다 유효한 모습으로 문서에 남는다.** 진행 중인 개발자에게 "옛 스펙대로 완주하지 말라"는 신호가 문서 어디에도 없게 된다. 폐기 마커가 그 신호다.

```
❌ 폐기 처리를 빼면 — 어느 쪽이 정본인지 알 수 없다
- [ ] [진행중,2026-08-01 10:00] 최근 30일 이내 정산건만 조회 (AC2)
- [ ] [생성됨,2026-08-03 14:20] 최근 90일 이내 정산건만 조회 (AC12)

✅ 폐기 처리
- [ ] [폐기됨,2026-08-03 14:20] 최근 30일 이내 정산건만 조회 (AC2)
- [ ] [생성됨,2026-08-03 14:20] 최근 90일 이내 정산건만 조회 (AC12)
```

- 위 예시에서 **AC 번호가 재사용되지 않은 것**을 보라. 정책이 대체되면 옛 AC(AC2)를 폐기하고 새 AC(AC12)를 마지막 번호 다음에 만든다. AC2 자리에 새 내용을 덮어쓰면 폐기된 태스크가 새 정책을 가리키게 된다.

- **판정이 애매하면 폐기 쪽으로 기운다.** 추가 작업으로 잘못 분류하면 옛 정책이 유효한 채 남아 잘못된 구현이 완주되지만, 폐기로 잘못 분류하면 이력에 폐기 줄이 하나 더 남을 뿐이다.

### 반입룰 (bring-in)

**작업 코드베이스에서 실행하는 절차다.** 서비스 코드를 만들다가 그 사이 바뀐 기획을 애자일 이슈에 반영하고, 필요하면 기존 코드 수정까지 제안한다(용어는 「용어 정의 — 반입」 참고).

> **역할 분담**: 바로 위 「기획(통합캔버스) 최신화 시 기존 이슈 반영 규칙」이 **"무엇을 어떻게 고치는가"** 를 소유한다. 반입룰은 **"누가·어디서·언제 그것을 돌리는가"** 만 소유한다. 대조 절차·삭제 판정·화면 변경 도출·태스크 상태별 처리를 여기서 다시 정의하지 않는다 — 두 곳에 적으면 한쪽만 갱신되어 어긋난다(정책 단일 출처 원칙).

**전제 — one-canvas는 별개 저장소다**: 작업 코드베이스와 완전히 분리된 저장소이므로 별도로 클론되어 있어야 한다. 애자일 이슈는 작업 코드베이스에 살고, 두 저장소를 잇는 것은 **실행 시 프롬프트가 주입하는 one-canvas 클론 경로 하나**다. 그 경로와 에픽 `캔버스:` 상대 경로를 합쳐 캔버스 파일을 찾는다.

- **클론 위치는 규정하지 않는다** — 환경마다 다르므로, 경로를 모르면 추측하지 말고 작업자에게 묻는다. 클론이 없으면 반입을 시작할 수 없다.
- 이슈 쪽에 캔버스 커밋 SHA를 적지 않는 이유도 이 분리 때문이다(「용어 정의 — 최신 대조」 참고).

#### 절차

1. **one-canvas 최신화** — one-canvas 클론에서 `git pull`. 이 단계를 건너뛰면 옛 캔버스를 정본으로 대조하게 되어 절차 자체가 무의미해진다.
2. **대상 에픽 선정** — **지금 작업 중인 코드에 대응하는 에픽만** 대상으로 삼는다. 저장소 전체 에픽을 매번 훑으면 반입이 무거워져 아무도 돌리지 않게 된다.
   - 대조는 캔버스와 이슈를 실제로 읽어야 하므로, **대상 에픽을 좁히는 것이 유일한 비용 통제 수단이다.**
   - 다른 에픽은 **손대지 않는다.** 뒤처졌는지 알려면 그 에픽도 읽어야 하므로, 확인하지 않은 에픽을 "최신"이라고 보고하지 않는다.
3. **대조·반영** — 「기획(통합캔버스) 최신화 시 기존 이슈 반영 규칙」을 **그대로 따른다.** 착수 전이든 착수 후든 조건 없이 위임한다 — 그 섹션이 3단계 대조·삭제 연쇄·화면 변경 도출·태스크 상태별 처리 전부를 규정하고 있다.
   - **대상 에픽의 하위 스토리는 전부 대조한다.** 어느 스토리가 최신인지 미리 알 방법이 없다. 차이가 없는 스토리는 "차이 없음"으로 끝나므로 제안에 오르지 않는다.
   - 진행 정도는 **스토리 frontmatter `status`와 태스크 상태 마커**로 판정한다. **에픽에는 `status`가 없다**(「문서 메타데이터」 참고) — 에픽 진행도는 하위 스토리와 태스크에서만 읽어낸다.
   - **화면이 바뀐 경우 프론트 태스크 도출을 빼먹지 않는다.** AC 문장이 그대로여도 배치·컴포넌트·카피는 바뀔 수 있으므로, AC 대조만으로 끝내면 화면 변경이 통째로 누락된다(「화면 변경 → 프론트 태스크 도출」 참고).
4. **제안 제출** — 수정안을 제시하는 데서 끝낸다. **에이전트는 애자일 이슈 파일을 직접 고치거나 커밋하지 않는다.** 반영 여부와 커밋은 작업자가 판단한다.

#### 제안 출력 형식

제안이 곧 산출물이므로, 작업자가 **아무것도 다시 유추하지 않고** 바로 적용할 수 있어야 한다. 항목마다 아래 4가지를 적는다.

| 항목 | 내용 |
|---|---|
| 대상 | 파일 경로 + 섹션/라인 (예: `settlement/epic-.../story-.../index.md` 「수락 기준」 AC14) |
| 변경 | 변경 전 → 변경 후. 라인 단위로 그대로 옮겨 붙일 수 있게 적는다 |
| 근거 | 캔버스의 **어느 화면·어느 소제목·어느 문장**과 어긋나는지. 추측이 아니라 캔버스에 있는 것만 |
| 분류 | 명세 수정 / AC 추가 / AC 폐기 / 태스크 직접 수정 / 태스크 신규 추가 / 태스크 폐기(후보) 중 무엇인지 |

- **근거는 캔버스 현재 내용을 가리킨다.** 커밋 SHA를 근거로 적지 않는다 — 작업자가 확인해야 하는 것은 "지금 캔버스가 무엇이라고 적고 있는가"이고, 그것이 별개 저장소의 커밋 ID보다 검증하기 쉽다.
- 태스크 라인에는 **출처 커밋을 병기하지 않는다.** 언제 들어온 태스크인지는 상태 마커의 타임스탬프가 담고, 무엇에서 나왔는지는 AC 참조와 UI 태그가 담는다.
- **폐기 제안은 확정과 후보를 구별해서 적는다.** 참조 AC가 전부 삭제된 태스크는 폐기 확정, 일부만 삭제된 태스크는 **폐기 후보**로 적고 판정 근거(어느 AC가 남아 있는지)를 함께 밝힌다.
- 이미 `done`인 스토리에 재작업이 필요하면 `status`를 `changed-after-done`으로 바꾸는 것도 제안에 포함한다.
- **대조했지만 차이가 없던 스토리는 목록으로만 밝힌다.** 무엇을 확인했는지 남지 않으면 작업자가 빠뜨린 스토리와 구별할 수 없다.

#### 코드 수정 제안 (선택)

애자일 이슈 반영과 별개로, 이미 구현된 코드가 최신 기획과 어긋나면 수정을 제안할 수 있다.

- **제안까지만 한다.** 코드를 직접 고치지 않는다. 어느 파일의 무엇이 기획의 어느 부분과 어긋나는지 짚는 데서 끝낸다.
- **화면 구현 코드는 UI 태그로 찾는다.** 폐기·수정 대상이 된 프론트 태스크의 UI 태그(컴포넌트 경로)로 실제 코드를 좁힌다.
- **디자인 시스템 작업은 제안에서 뺀다** — 캔버스에 "디자인 시스템 미보유" 항목이 있어도 컴포넌트 신설·variant 추가·공용화는 애자일 이슈의 범위가 아니다(「태스크 범위에서 제외되는 작업 — 디자인 시스템」 참고). 다만 `신규 필요` 외 3분류는 화면 영역 자체가 범위에 남으므로 그 부분 코드 수정은 제안 대상이다.
- 근거 없이 추측해서 고치라고 하지 않는다. 캔버스에 적힌 것만 근거로 삼는다.

#### 반입룰 실행 프롬프트

```
작업 코드베이스에서 반입을 수행해줘.

[1] one-canvas 클론에서 git pull 로 최신화해줘.
    one-canvas는 이 코드베이스와 별개 저장소야. 클론 경로는 <one-canvas 클론 경로>.
    (경로를 안 알려줬거나 클론이 없으면 추측하지 말고 물어봐)
    캔버스 파일은 이 클론 경로 + 에픽 「캔버스」 줄의 상대 경로로 찾으면 돼.
[2] 그 클론의 agile-issue/agile-issue-rule.md 「반입룰」 섹션과
    「기획(통합캔버스) 최신화 시 기존 이슈 반영 규칙」을 먼저 읽어줘.
[3] 지금 작업 중인 코드에 대응하는 에픽 하나를 골라, 그 에픽 index.md +
    하위 스토리 index.md 전부 + 캔버스 최신본을 읽고 대조해줘.
    - 커밋 SHA나 diff 범위는 쓰지 마. 캔버스 HEAD가 정본이야.
    - 대조 대상은 캔버스 파생 항목만. 아래는 캔버스에 없는 게 정상이니 건드리지 마:
      에픽 「에픽 정책」 · (보강) 표시된 AC · 태스크 내용 · 테스트
    - 어긋난 곳을 변경 / 신규 / 삭제로 분류해줘.
    - 다른 에픽은 읽지도 손대지도 마. 확인 안 한 에픽을 "최신"이라고 말하지도 마.
[4] 삭제로 판정된 AC가 있으면 연쇄까지 처리해줘.
    - 표시 없는 AC인데 캔버스에 대응 GWT가 없는 경우만 삭제야.
    - 그 AC 번호를 grep 해서 참조한 태스크·테스트를 찾아줘.
    - 참조 AC가 전부 삭제된 태스크는 폐기 확정, 일부만 삭제면 폐기 후보로 적어줘.
    - AC 번호는 재사용하지 마. 폐기한 번호는 자리에 남기고 새 AC는 마지막 번호 다음으로.
[5] 화면이 바뀌었으면 프론트 태스크를 따로 도출해줘.
    - AC 문장이 그대로여도 배치·컴포넌트 태깅·카피는 바뀔 수 있어. AC 대조만으로 끝내지 마.
    - 태스크의 [ui: 화면N ○ 카테고리/컴포넌트] 태그로 영향 범위를 좁혀줘.
    - 영역 추가 → 신규 태스크 / 영역 삭제 → 폐기 후보 /
      컴포넌트 교체·배치 변경 → 착수 전이면 직접 수정, 착수 후면 폐기+대체 또는 수정 태스크 추가
    - 새로 만드는 프론트·앱 태스크에는 UI 태그와 AC 참조를 반드시 달아줘.
    - 디자인 시스템 자체를 손대는 작업(컴포넌트 신설·variant 추가·공용화)은 도출하지 마.
[6] 수정안을 만들어줘. 파일을 직접 고치거나 커밋하지는 마. 제안까지만.
    - 파일 경로 / 변경 전→후 / 근거(캔버스의 어느 화면·소제목·문장) / 분류를 항목마다 적어줘
    - 대조했는데 차이가 없던 스토리는 목록으로 밝혀줘 (빠뜨린 것과 구별되게)
    - done 인 스토리에 재작업이 필요하면 status: changed-after-done 제안도 넣어줘
[7] 이미 구현된 코드가 최신 기획과 어긋나면 그것도 짚어줘 (수정은 하지 말고).

근거 없이 지어내지 마. 캔버스에 적혀 있는 것만 근거로 쓰고,
판단이 안 서면 멈추고 물어봐.
```


## 계층별 작성 주체(Role) 매핑

| 계층 / 산출물 | 작성 주체 Role |
|---|---|
| 도메인 `index.md` | 기획자 |
| 에픽 `index.md` | 기획자 |
| 스토리 `index.md` (설명·정책) | 기획자 |
| 스토리 `index.md` 내 **태스크** 섹션 | 개발자 (backend / frontend / app) |
| 스토리 `index.md` 내 **성공 / 실패 테스트** 섹션 | 기획자/QA |

> **내용 작성 시 Role을 반드시 분리하여 각 관점으로 나누어 작성한다.**
> Role은 4종 — **기획자  · 개발자 · QA** — 이며, 개발자는 실무상 프론트엔드 / 백엔드 / 앱으로 세분화된다(Role 정의 참고).
> Role 정의는 각 관점에서 **무엇을 고려해 작성할지** 정의한 참고 기준이다.


## Role 정의

### 기획자 (Product Owner / PM)
- **목적**: 기능의 비즈니스 목표를 정의하고 제품 정책과 사용자 경험(UX)을 설계한다.
- **산출물**:
  - **User Story**: 고객 관점의 기능 요구사항 정의
  - **기능 정책**: 화면 구성 요소, 입력 제한, 비즈니스 규칙 명시
  - **수락 기준(Acceptance Criteria)**: 기능 완료를 판단할 최종 조건 리스트

### 개발자 — 프론트엔드 (Frontend Engineer)
- **목적**: 웹 브라우저 환경에서 사용자가 마주하는 화면과 UI 인터랙션을 구현한다.
- **산출물**:
  - **UI 컴포넌트 마크업**: 디자인 시스템/Figma 반영, 반응형 레이아웃
  - **클라이언트 상태 관리**: 입력 필드 상태, 실시간 유효성 검사, 전역 상태 처리
  - **웹 API 연동**: API 통신, 로딩/에러 UI 대응

### 개발자 — 백엔드 (Backend Engineer)
- **목적**: 데이터를 안전하게 저장·가공하고, 서비스의 비즈니스 로직을 처리하는 서버 시스템을 구축한다.
- **산출물**:
  - **DB 데이터 모델링**: 테이블 설계, 인덱스 및 스키마 변경 정의
  - **API 스펙 정의**: RESTful/GraphQL 규격 및 API 문서(Swagger 등)
  - **서버 비즈니스 로직 구현**: 데이터 검증, 보안 처리, 비즈니스 에러 코드 정의

### 개발자 — 앱 (AOS / iOS Mobile App Engineer)
- **목적**: 모바일 기기 환경에 최적화된 네이티브 앱 화면과 기능을 구현한다.
- **산출물**:
  - **네이티브 UI/UX 구현**: 모바일 OS 가이드라인 준수, 화면 전환 애니메이션
  - **디바이스 기능 제어**: 푸시 알림, 로컬 저장소, 기기별 해상도 대응
  - **앱 API 연동**: 모바일 네트워크 최적화 통신, 앱 전용 예외 처리

### QA (Quality Assurance Engineer)
- **목적**: 기획서와 수락 기준을 바탕으로 결함을 찾아내고 서비스 품질을 보증한다.
- **산출물**:
  - **테스트 케이스(TC) 설계**: 정상 시나리오 및 예외 상황(Edge Case) 도출
  - **기능·회귀 테스트**: 구현 기능 검증, 크로스 브라우징 및 기기별(웹/앱) 호환성 체크
  - **버그 리포팅**: 지라 버그 티켓 생성을 통한 결함 추적 및 재테스트(Retest) 조건 정의

## 참조 자료

### 화면 목록
> 화면 구현 시 아래 앵커로 캔버스의 해당 화면을 바로 연다. 앵커는 위 `캔버스:` 파일 기준 — `<캔버스 파일>#<앵커>`
> (화면 없는 캔버스(B유형)면 이 표를 생략한다)

## 수락 기준 (Acceptance Criteria)
> Given-When-Then 시나리오로 작성한다. 정상/예외 등 조건 분기는 시나리오를 분리한다.
> 이슈에서 보강한 AC에는 `(보강)`을 붙인다 — 표시 없는 AC는 캔버스 GWT 계승분이며 대조 대상이다.
> AC 번호는 영구 불변. 재번호하지 않고, 폐기된 번호를 재사용하지 않는다.
- [ ] **AC1** Given <사전 조건>, When <행동>, Then <기대 결과>
- [ ] **AC2** (보강) Given <캔버스에 없는 예외 조건>, When <행동>, Then <기대 결과>
- [ ] ~~**AC3**~~ [폐기됨,YYYY-MM-DD HH:mm] <캔버스에서 삭제된 정책 — 번호는 자리에 남긴다>
- ...
